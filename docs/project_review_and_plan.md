# 项目评审与改进记录

本文记录旧架构的评审和改进过程。当前开发按 [Go 增量日志与 Rust 快照无人值守计划](golog_unattended_plan.md) 执行。

## 当前定位

Kerniva 当前为 Redis 协议兼容服务与自研 Rust KV 内核组成的原型，已经完成一轮工程化改造。主要链路为 TCP 请求、RESP 解析、有界连接队列、命令执行、逻辑数据库、C ABI、Rust segment log。

本轮以工作区现有代码为依据实施，保留多数据类型、双网络入口和自研内核方向。原型功能完善与生产规模验证需要分别持续推进。

2026-11-15 的毕设阶段聚焦同步持久化下的读取尾延迟，已实现 Go 私有暂存与提交后发布、Rust writer/index 分离，以及后台 TTL 的非阻塞扫描和启停协调。具体设计、适用条件与三虚拟机后续方案见 [毕设设计说明](thesis_read_isolation_design.md)。下文五阶段记录保留此前工程化改造的验收背景。

## 整体逻辑

1. cmd/server 加载 YAML 和环境覆盖，校验后初始化日志、可选 pprof 和服务。
2. std/gnet 接收 TCP，增量解析 RESP，将独立命令加入连接有界队列。
3. 连接 worker 有序执行，命令协调门控制单 key 并发与复合命令隔离。
4. command 注册表处理参数、类型命令和 Lua。server 处理连接状态、事务、PubSub 和阻塞等待。
5. DBManager 管理独立逻辑库。数据库协调分片缓存、TTL、内存预算、WATCH 和变更前状态。
6. 持久化操作暂存为批次，Rust append 并执行同步策略成功后发布索引。失败时返回错误并恢复 Go 状态。
7. 读取先查 Go 缓存，按需从 Rust 定位读取、验证和解码。后台抽样过期并定期执行条件维护。
8. 停止取消连接和阻塞请求，关闭网络与数据库，同步引擎并关闭日志。

模块、数据流和格式分别见 [架构说明](kerniva_engine_architecture.md) 与 [设计文档](kerniva_engine_design.md)。

## 五阶段交付

### 第一阶段，语义和并发正确性

已完善数据库操作与关闭的协调、可变输入与输出所有权、多 key 变更日志、失败回滚、重复 DEL 计数和 WATCH 版本管理。

命令执行使用共享/排他门协调普通请求、复合命令和 EXEC。事务队列提前校验并复制参数。网络回调与命令执行分离，阻塞命令参与连接取消和退出。

Stream 完整状态序列化覆盖消费组、PEL、消费者及投递计数。读取兼容旧格式。针对冷启动、命令状态和持久化失败增加回归。

### 第二阶段，持久化和崩溃恢复

新增单记录原子 WriteBatch 和 C ABI，Go mutation journal 在同库数据库操作内合并提交。sync 每次提交执行 sync_all。打开失败通过受检构造和服务启动链路传播。

强化数据目录进程锁、尾部与损坏分类、长度和 checksum、checkpoint v2 原子替换，以及部分 append 失败截断回滚。快照和 iterator 持有目录租约，读取取得句柄后允许回收并发。

Reset 改为原生 Clear marker，写入固定 20 字节日志后清空当前索引。它支持旧快照视图，避免枚举历史 value 和按 key 构建删除批次。

### 第三阶段，资源和安全边界

配置严格识别 YAML 字段及非法环境值，补全枚举和预算校验。max_memory 传入每个逻辑库，持久化缓存卸载保留逻辑 key。

Lua 使用库白名单、250ms 超时、指令预算、脚本/参数/结果/缓存上限及采样分配预算。网络输入、事务队列、发布订阅输出和阻塞生命周期具有相应边界及测试。

日志实现等级过滤、文件轮转和关闭。pprof 跟随进程退出，默认监听配置为本机地址。

### 第四阶段，构建和交付验证

修复本机 Go/Rust GNU 链接环境，使用 Go 1.25.8、Rust 1.95 和完整 MinGW GCC 工具链验证。实现跨平台动态库加载，构建脚本产出服务端、客户端和原生库，测试脚本在 Rust 和 Go 任一步失败时返回失败。

Windows 控制脚本使用停止请求文件协调退出。Unix 使用信号等待退出并传播超时。清理脚本的目标限定在 bin/build/dist。新增 LF 属性固定 Unix 脚本和 Makefile 行尾。

CI 配置 Windows、Linux 和 macOS 原生测试及 Go race。远程 CI 尚待仓库实际运行。本机 Linux/macOS Go 交叉编译提供编译覆盖，原生动态库执行由平台 CI 继续验证。

### 第五阶段，性能治理和文档

新增小 KV TCP benchmark，支持 1/16/64 并发、32B SET/GET、逐回复验证和 p50/p95/p99。最终构建完成 24 组本机测量。

优化网络响应合批、gnet 唤醒及流水线缓冲管理。ZSet 单成员变更二分定位并移动切片，批量添加一次排序。背景空间回收改为按 sealed garbage 比例触发，减少全 live 段重复改写。

同步 README、整体框架、存储格式、提交边界和复现方法。实测数据见 [性能验证](performance_validation.md)。

## 面向小 KV 高并发和低尾延迟的实验

当前毕设实验优先验证提交等待与无关读取的隔离，使用固定到达率混合负载、重复轮次与阶段消融。以下 group commit 和维护预算化方案作为后续研究候选。跨库恢复、版本索引资源治理和兼容性各自设置回归和验收。

group commit 可先扫描 0 / 25 / 50 / 100 / 250 微秒等待窗口，结合每批操作数和字节上限。实验初始上限可选择 32 操作、64KiB，任一条件达到即提交。等待队列同时限制请求数和总字节，队列满时反馈回压。

每批 append 和同步成功后才能发布缓存、WATCH 版本及成功回复。失败需要统一处理本批所有等待者，并验证回滚或引擎拒写状态。当前符合并发条件的持久化普通 SET 已使用私有暂存，其他变更由数据库排他锁协调。聚合原型还需设计入队与单写者执行组织，维持读取可见性。

使用相同的 32B TCP workload，增加重复轮次，按 1 / 16 / 64 并发记录每个请求的完整回复延迟、实际批次大小、排队深度和 fsync 数。绘制 p99 与吞吐曲线选择窗口，保留窗口为 0 的同步基线。批次吞吐还需换算为独立请求的确认时点和端到端延迟。

维护预算化实验分别限制每次搬迁字节、扫描条目和锁持有时间，并在长期覆盖写入、快照 pin 与冷 TTL 场景中测量磁盘放大和 p99。全量 checkpoint 可独立评估增量快照原型。

MVCC 和新索引会改变内存、格式及生命周期模型，宜通过独立原型和故障测试作决策。这些均为候选设计，当前交付为原型工程化改造及基线测量。新颖性与跨产品优势需要独立论证和匹配条件的实验。
