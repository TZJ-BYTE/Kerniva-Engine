# ADR 0003 · 已封存日志与快照的异步复制

状态为已采纳的 WSL 原型。记录日期为 2026-11-24。

## 背景

Go 主节点同步确认写入，Rust 自主生成某个提交序号的快照并回收覆盖日志。毕业设计的复制演示需要表现持续写入、异步追赶，以及副本断线跨过回收点后的恢复。主节点的写入和确认继续复用现有路径。 [主节点架构](adr-0002-thesis-go-cache-rust-segments.md)

## 决策

~~~mermaid
flowchart LR
    C[RESP 客户端] --> P[Go 主节点]
    P --> A[(活跃日志)]
    A --> D[(封存日志)]
    D --> M[Rust 快照进程]
    M --> S[(已发布快照)]
    D --> X[源端复制侧车]
    S --> X
    X --> R1[从节点 A]
    X --> R2[从节点 B]
    R1 --> H1[本地只读 HTTP]
    R2 --> H2[本地只读 HTTP]
~~~

源侧车读取逻辑库的当前快照和连续封存段。选择文件时与 Rust 快照发布使用同一把恢复锁，并在释放锁前打开文件。之后即使原文件被回收，已经打开的 Linux 文件描述符仍可供传输。侧车的源 ID 持久保存在主节点日志根目录。

副本按各库的已发布序号向同一来源拉取新段。当该序号小于主节点的快照截止序号时，源端默认提供已发布快照和后续封存段。原型逐次拉取最多 128 个文件，以 64 MiB 为发起下一文件前的停止边界。单个完整文件可以超过该边界。

Rust 整理进程可用 `--retain-covered-segments N` 保留近期日志，默认值为 0，每库最多 16 段、合计 64 MiB。保留的是恰好接到已发布快照截止序号的连续后缀。非空副本的游标能从段边界完整接到截止点时，源端可继续发送增量。跨度超过保留范围、游标落在段内和空副本首次同步都使用快照。选中的已覆盖段无法打开或截断至只剩文件头时，源端切换为快照及后续封存段。候选增量文件在 Rust 校验阶段失败且源端给出更新快照时，副本用原游标再请求一次快照，发布成功前仍可读旧视图。

副本将文件写入新一代目录，通过 Rust 恢复库验证帧、校验和与恢复序号，再同步文件和目录并切换本地 CURRENT。内存读视图在目录同步成功后推进。传输截断、校验失败、换源和目录同步失败保留上一份读视图。源端读取文件与客户端查询均使用 Go，C ABI 发生在副本安装和重启恢复时。

普通增量批次复用已发布的日志文件。Rust 校验新段并按键折叠覆盖、删除和清空操作，再通过 C ABI 分块导出。Go 在发布 CURRENT 前解码和暂存变化，在目录同步成功后通过一把写锁同时更新读视图与应用序号。空副本首次恢复、安装快照、在线换代和重启仍走完整恢复，重新校验所用历史数据。旧版 Rust 库缺少增量接口时也走完整恢复。

持续在线的副本也可以切换到已追过的主节点快照。当可回收的本地日志至少为 64 MiB 且至少为快照大小的两倍，副本请求该快照，找出本地仍需保留的尾段并通过硬链接复用。在相同序号发布新代后回收被覆盖的旧日志。同一逻辑库两次请求快照至少间隔 30 秒，正常的增量拉取可以继续。

常驻副本为每个配置的逻辑库启动一个轮询循环。每库完成一次拉取或失败后，独立等待 `--interval` 再试。同库共用一个可取消的入口，单轮 `Poll` 与常驻循环并用时也按库串行。各库共享副本根目录中的 `UPSTREAM`，首次绑定来源须在该库发布 `CURRENT` 前完成持久化。关闭时先取消轮询，待在途操作退出后释放根目录锁。

使用标准 Go HTTP transport 时，每个副本拥有自己的空闲连接池。默认每主机空闲连接上限取配置的逻辑库数与 2 中的较大值，全局连接上限与显式的每主机设置继续生效。16 库对照中，源端保留的连接从 2 条增加到 16 条，每次成功空轮询的 Go 分配减少 40.3%–44.8%。[连接分配与封存后可见延迟](../verification/replica-idle-polling.md)

每个逻辑库在自己的拉取门内复用一个响应 reader，首次解析响应时分配缓冲，所有退出路径解绑响应体并清空预读状态。同库下一轮可重新绑定，其他库无需等待该 reader。16 库预热后合计新增 64 KiB 缓冲和 1,408 字节结构字段，每次成功空拉取比连接池基线再少分配约 4.1–4.2 KB。[读缓冲与真实有载复验](../verification/replica-reader-reuse.md)

副本启动参数 `follow --snapshot-concurrency N` 控制同一进程同时传输和安装的快照数。默认 `0` 沿用各库独立拉取的调度。设置正数时，首次补齐、在线换代和损坏增量后的快照恢复共用名额。普通增量和空轮询可独立推进。

开启上限后，副本在普通拉取上附加 `defer_snapshot=1`。源端在需要传输快照时返回无载荷的 HTTP 204 和 `Kerniva-Snapshot-Required: 1`。副本关闭探测响应，取得名额后按原游标重新请求并校验实际收到的清单。等待名额期间可取消，发出网络请求后重新开始统计传输空闲时间。旧源会直接发送快照，名额已满时副本关闭响应，排到后重新拉取；旧源在收到取消前可能已经发送部分字节。

成功安装时，名额覆盖下载、校验、替换 `CURRENT` 和同步父目录。故障会释放名额；原有游标恢复及读视图发布规则继续生效。此参数分别作用于每个副本进程。

全量安装及离线重启通过同步回调借用 Rust 的单行键值缓冲，Go 在回调返回前解码出拥有独立存储的读视图项。原生行在回调退出时释放；主库的恢复回调仍可保留 Go 拷贝。两对真实传输在默认并发下分别节省 118 和 156 MiB 峰值 RSS。[配对实测](../verification/replica-recovery-memory.md)

在 Linux 上诊断副本内存时，可只给目标 `follow` 进程设置 `KERNIVA_GOLOG_MEMORY_TRACE=/absolute/path/to/trace.jsonl`。每个窗口使用独立文件。记录包含逻辑库、代、阶段、单调时钟、RSS、Go 堆和累计分配字节。快照恢复中，`rust_handle_ready` 表示原生恢复句柄已就绪，至 `rust_rows_restored` 之间会逐行跨 ABI 传值并建立 Go 读视图。诊断已启用时，向该副本发送 `SIGUSR1` 可补采一条进程读数。采样沿用 Go 自然 GC。各库共享同一进程，多个库同时恢复时其阶段记录中的内存增量可能重叠。

## 关键接口

| 接口 | 输入与语义 |
| --- | --- |
| 源端 `GET /pull` | 传入 `db`、`after` 和已知 `source`。在线换快照附带截止序号 `rebase`，损坏的保留段可用 `snapshot=1` 请求更新快照。返回带长度的版本化 JSON 清单和按清单排列的原始文件。 |
| 副本 `GET /status?db=0` | 返回 `ready`、`source`、`sequence`、`snapshot`、`installs`、`bootstraps`、`rebases` 和 `last_error`。计数按进程统计。 |
| 副本 `GET /get?db=0&key=name` | 已同步字符串返回原始字节。缺失或过期返回 404，尚未建立读视图返回 503，其他数据类型返回 409。 |

## 备选方案

- **直接复制活跃日志**可以缩短同步等待，需要新增可并发读取的已同步文件偏移，处理尾部回滚与轮转。封存段提供了当前格式已有的稳定边界。
- **客户端写入时等待副本**可提高写入确认的副本覆盖范围，延迟受副本和网络影响，同时引入同步失败处理。当前目标以本机写入延迟与可验证的异步恢复为主。

## 影响

复制原型绑定本地回环地址，支持在单个 WSL 内核中运行一主两从。服务保持异步语义，各逻辑库分别推进，复制延迟受段封存周期和轮询间隔影响。普通增量只读新段的数据，副本应用开销随本批变化规模增长。快照与重启恢复仍随全库规模增长。快照传输门槛保留了连续增长场景中的空间与网络权衡。演示只读入口采用 HTTP，项目范围暂定单主、静态副本和手动恢复。

## 从备份恢复主库

主库正常重启时保留原来源 ID。将较早的备份恢复为新主库时，日志序号可能复用，先轮换恢复目录的来源 ID。使用一致的离线备份和独立的数据目录，停止访问这份恢复目录的复制侧车，再执行轮换。

~~~bash
./bin/kerniva-replica rotate-source-id --root "$restored_data/go-log-v1"
~~~

命令在目录同步成功后打印新 ID。新版复制侧车运行时持有共享锁，正在服务的目录会拒绝轮换。轮换过程中若文件已经替换、最后的目录同步失败，错误会给出新 ID，须等目录同步成功再开放新来源。升级前的侧车应先停止。这个命令只处理来源 ID，主库和旧副本的数据目录保留各自的文件。

将主服务的 `data_dir` 指向恢复目录，然后以该目录启动源侧车。新副本从独立空目录开始跟随。带原来源 ID 的副本会保留旧的可读数据和游标，并通过 `last_error` 报告来源变化。直接沿用备份中的来源 ID 有复用旧序号的风险，复制协议以操作员完成来源轮换为前提。

## 运行与验收

从 WSL ext4 仓库执行。

~~~bash
bash scripts/build.sh
python3 -B scripts/golog-replica-check.py --network gnet
python3 -B scripts/golog-replica-check.py --network std
python3 -B scripts/golog-replica-check.py --network gnet --rebase --timeout 30
python3 -B scripts/golog-replica-check.py --network gnet --source-restore --timeout 20
python3 -B scripts/golog-replica-check.py --network gnet --stress --stress-seconds 60 --timeout 20
python3 -B scripts/golog-replica-check.py --network gnet --stress --stress-seconds 60 --stress-retain-segments 8 --timeout 20
~~~

脚本启动实际主服务和源侧车，以及各有独立目录的两个副本。主动结束副本 B，主节点继续写入，副本 A 通过增量追赶。Rust 回收日志后，B 用快照及尾段恢复。随后强制重启主服务和侧车并验证持续追赶。`--rebase` 额外生成满足门槛的历史日志，核对在线副本的换代、回收和后续追赶。`--stress` 用实际并发请求在从端落下部分日志后终止 B，并验证旧游标恢复、重新入队与逐键结果。原生测试另外覆盖损坏数据、截断响应、目录同步失败、来源不符和回收期间的文件读取。 [测试记录](../golog_grouped_replica_report.md)
