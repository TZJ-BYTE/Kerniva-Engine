## 定位结果与实现改动

### Rust 目录锁

原目录锁依赖文件关闭释放。当文件描述符仍有副本存活时，关闭原文件可能留下 flock，导致最后一个引擎实例退出后重新打开目录仍返回 Locked。确定性测试通过复制文件描述符复现该问题。

新增 DirectoryLock，在最后一个共享锁拥有者释放时显式 unlock。引擎与快照租约通过 Arc 共享拥有权，快照仍可延长目录占用时间。旧实现的回归测试失败，新实现通过 Windows 验收和 Linux 20 轮完整并行测试，共执行 820 个 Rust 测试用例。

该可靠性修复纳入 start 与 candidate 的公共起点。

### Go 提交等待

原字符串 SET 在 Rust 同步提交期间持有 256 个热点分片锁之一。另一个 key 即使只读已提交缓存，只要映射到同一分片，也会等待这次写入。

候选实现为正在提交的 key 登记完成通知。写入值保持私有，SET 释放热点分片锁后进入 Rust 提交。提交成功后重新取得锁，发布缓存与版本通知，再唤醒同 key 请求。失败时保留旧缓存、释放预留预算并唤醒等待者。生命周期读锁跨越提交与发布，Clear、Close 继续等待正在执行的操作完成。

无关 key 可以继续读取已提交缓存。同 key 操作等待提交结束后重新检查条件。代价包括每次合格 SET 的通知对象与热路径的 pending 映射查询，相关吞吐、内存和尾延迟以正式实验评价。

确定性屏障测试在旧实现中复现同分片不同 key 的 GET 被阻塞，新实现通过 Windows 与 Linux 的重复 race 验收。CLI、演示和空 bulk 解析属于同轮交付内容。正式混合负载使用现有快速 RESP 请求解析入口。

### 等待链路证据

两组高负载 Linux 基线分别采用 std、95% GET、15,000 请求/秒，以及 gnet、80% GET、3,750 请求/秒，每组 3 轮，60 秒正式测量与 15 秒预热。六轮中部分窗口出现大量超时，原始失败分母完整保留。

独立诊断运行使用 goroutine 栈采样与 strace。阻塞 GET 栈位于 Go 热点分片读锁，写入栈主要位于 Rust writeBatch 的外部调用。同步调用与维护共用 Rust writer，延长 SET 的锁占用后，无关 GET 受到同分片等待影响。

strace 会增加开销，诊断进程的父 PID 还是 strace。该组用于等待链路诊断。维护事件出现在少数采样中，且队列在正式计时开始时已经存在，现有数据不足以认定 checkpoint 或 compact 主导尖峰。客户端窗口按计划发送秒分桶，栈和同步跟踪按实际时间采集，客户端排队使逐秒归因存在不确定性。

代码审阅还发现 INFO 会申请排他执行门，持久化统计可能等待 writer。本轮正式运行器在开始计时前和客户端退出后采集 INFO，每秒资源样本读取 /proc。归档的旧 Windows 运行器也只在前后采集 INFO，历史波动的归因保留原有不确定性。

## 保留问题

当前性能改动覆盖已缓存、无 TTL、无淘汰的字符串同步写路径。冷读、复杂类型和生命周期排他操作仍可能影响并发读取。Rust writer 仍串行执行提交，同步持久化吞吐需要根据实测到达率评价。

当前毕设可以围绕同步持久化的小键值缓存读取隔离组织设计、正确性证明、Redis 对照和失效边界。后续最小实验优先区分专用读连接与混合连接排队的影响，再采集有开关的同步及维护事件时刻，核验持续尖峰和同热点回退。Rust 已提交索引拆分在本轮热缓存负载中的独立性能收益仍待匹配场景验证。

跨数据库事务、Lua 的跨库崩溃原子性与 MOVE 窗口属于现有边界。分布式复制、跨节点一致性和三虚拟机故障实验保留为后续设计，本轮交付为单机研究与演示。
