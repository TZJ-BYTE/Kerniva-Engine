# Go 日志与 Rust 快照 WSL 实测

2026-11-24 在本机 WSL 2 Ubuntu 26.04、Linux ext4、i9-14900HX 上执行。WSL 可见 32 个逻辑 CPU。Go 1.26.8、Rust 1.95.0、Redis 8.0.5。旧 Kerniva 使用冻结的 `a433959` Go 产物及配套 Rust 库，和候选路线起点 `edd3f90` 之间仅有文档变更。各对照依次在同一 WSL、同一 loopback 和 ext4 环境运行。

## 方法

- 主对照预置 100,000 个键、32 字节值、64 个 TCP 连接，95% GET、5% SET。均匀键和始终访问单个热点键分别测。每档每方案 3 轮，固定到达率，预热 1 秒、采集 5 秒。每轮按同一随机种子配对并轮换测试次序。
- 纯内存组关闭持久化。缓冲组对比 Go `none`、旧 Rust `none` 与 Redis AOF `no`。同步组对比确认前同步的 Go、旧 Rust 和 Redis AOF `always`。Go 每批请求单独同步，Redis 可以把同一事件循环的多条写入合并同步，测的是两套确认策略的实际实现。Redis 通过 `CONFIG GET` 核对配置，常规测量关闭快照和自动重写。 [Redis 持久化文档](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
- 延迟从计划发出请求到回复读取完毕，含客户端排队。数值为各轮中位数。成功请求吞吐使用测量及排空的实际耗时，失败率以计划请求作分母。每轮零失败、实际完成达到目标的 98% 且队列无持续增长才达标。采样粒度和短窗口限制了对极端尾延迟的推论。

## 主对照

完成 132 个窗口，20,145,000 次计划请求全部完成。下表为均匀负载的高档位，表内各方案在对应档位均为 3/3 达标。

| --- | --- | ---: | ---: | ---: | ---: |
| 内存 | Go | 89,945 | 3.916 / 7.274 | 3.801 / 7.324 | 74.3 |
| 内存 | Rust 主存原型 | 89,945 | 4.030 / 7.258 | 4.030 / 7.078 | 46.2 |

| 缓冲 | 旧 Rust 分段日志 | 89,944 | 4.424 / 8.913 | 4.588 / 9.241 | 87.3 |

新方案在同步均匀读多写少场景的 GET p99 比 Redis 低 48.2%，SET p99 两者均为 3.072 ms。将访问集中到单个键时，新方案和 Redis 的 GET p99 分别为 2.236 和 2.245 ms，Rust 主存同步原型为 1.294 ms。缓冲日志高档中，Redis 的 GET、SET p99 及进程 CPU、RSS 更低。新 Go 日志和旧 Rust 日志在多数高档场景承载量相当，短窗中尾延迟和 RSS 有所下降。

## 自主整理

Rust 在 6 个主对照窗口中自行发布快照。缓冲场景的首轮快照覆盖序号 898 并回收 131 段、8,349,921 字节。同步窗口覆盖序号 390 并回收 130 段、8,284,450 字节。两组保持 3/3 达标。缓冲 10,000 请求/s 时，开始维护前后的 GET p99 中位数为 1.483 和 1.470 ms，SET p99 为 1.532 和 1.499 ms。同步 1,500 请求/s 时，GET p99 均为 1.217 ms，SET p99 从 3.187 到 3.244 ms。每个整理窗口另有普通 Go 日志窗口作为控制。

维护对照将段大小设为 64 KiB，并把 Rust 触发门槛降到 1 字节或 1 秒，以确保测量期间实际发生维护。常规压测和发布配置的封存大小为 4 MiB。进程 RSS 为采样峰值，短时子进程或瞬时峰值可能落在采样间隔内。

另做 24 个 8 秒窗口，对照新 Go 日志、Go 加 Rust 自主维护、Redis AOF、Redis AOF 人工重写。1,104,000 次计划请求均完成，6 个 Rust 窗口观察到清单切换，6 个 Redis 窗口观察到一次成功重写。同步 1,500 请求/s 时，Rust 整理期间 GET/SET p99 为 1.217/2.867 ms，Redis 重写期间为 2.073/3.359 ms。缓冲 10,000 请求/s 时分别为 1.466/1.532 ms 和 1.475/1.483 ms。手动重写用于使维护事件落在测量窗口，原始 INFO 记录实际起止状态。

## 重启恢复

通过 TCP 写入 100,000 个键及 64 字节值，同步提交后完整覆盖两轮，再删除 10,000 个键。对同一数据目录，在整理前后各重启三次，测量启动到第一次 TCP PONG 的时间，保留操作系统缓存。每次重启都核对 90,000 个最新值、10,000 个删除结果和全量键值摘要。

| 状态 | 三次启动时间，ms | 中位数，ms | 逻辑文件大小 |
| --- | --- | ---: | ---: |
| 回放 9 个封存段 | 227.25 / 204.77 / 189.54 | 204.77 | 33,908,580 B |
| 读取全量快照 | 133.59 / 120.84 / 141.72 | 133.59 | 10,710,041 B |

Rust 从启动到完成整理用时 164.76 ms，截止序号 2,425。它回收 9 段共 33,908,572 B，写出 10,710,028 B 的全量快照。整理后的启动中位数缩短 34.8%，逻辑文件大小减少 68.4%。

## 同步写入压力

将写比例提升到 50%，继续使用 100,000 键、64 连接、均匀键及每轮 5 秒的固定到达率，完成 18 个窗口。结果显示新方案的同步写上限在这个负载下明显受每批文件同步影响。每格为实际请求/s 和两轮累计失败数。

| 目标请求/s | 新 Go 日志 | 旧 Rust 分段日志 | Redis AOF `always` |
| ---: | ---: | ---: | ---: |
| 3,000 | 2,829 · 0/30,000 | 1,885 · 7,095/30,000 | 2,999 · 0/30,000 |
| 6,000 | 2,576 · 23,928/60,000 | 2,611 · 23,455/60,000 | 5,997 · 0/60,000 |
| 10,000 | 2,503 · 64,955/100,000 | 2,640 · 63,045/100,000 | 9,994 · 0/100,000 |

Go 在 3,000 请求/s 的两轮均积压，排空后完成全部请求，GET p99 中位数为 614.5 ms。Redis 三档均达标。同步小键值且读多写少的结果与写密集组对应不同负载比例。

## 正确性与交付

- Windows 与 WSL 上通过 Rust 测试、Go race 及 net/gnet 实际 TCP 回归。Go 强制终止测试覆盖同步确认后的批量写入、快照后更新、删除、TTL、列表和哈希。
- Rust 维护子进程分别在快照完成同步、`CURRENT` 完成同步、第一段已回收时被强制终止。每次均验证追加到该截止序号之后的数据还能恢复，维护重新启动后能继续回收。
- 使用发布配置 `config.golog.yaml` 验证 16 个逻辑库入口。`SELECT 15` 写入、Rust 自主发布快照和 Go 重启读取均通过。
- 新后端采用全量装载 `load_all`。当前平台实测为 Windows 和 WSL Ubuntu 26.04。Ubuntu 22.04、物理掉电和跨节点故障属于额外验收环境。
