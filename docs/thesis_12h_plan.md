- 客户端计划发送、实际发送、完整响应、排队、超时与重连，保留 GET/SET 各自的统计。
- Go 执行门、全局操作锁和热点分片锁的等待，记录冷读回退、TTL 扫描及维护事件。
- Rust writer 与 index 锁等待、同步调用耗时、checkpoint 和 compact 的开始结束及处理量。

## 5. 根据证据选择优化

本阶段最多推进一个主要瓶颈的修复，并为该修复完成针对性验证。

| 观测到的首要原因 | 优先处理方向 | 必须核对的行为 |
| --- | --- | --- |
| 冷读、TTL 或维护请求造成全局协调排队 | 缩短必要的排他区间，调整维护调度或回退路径 | 锁顺序、到期可见性、同键顺序、Clear/Close |
| checkpoint 或 compact 长时间占用 writer | 缩短写入暂停区间，调整已提交视图捕获与维护节奏 | 恢复边界、段引用、旧段回收、失败处理 |
| 高频同步提交使写队列持续积压 | 评估有界批量同步的收益和实现复杂度 | 每条成功回复对应的持久化边界、批次失败与关闭唤醒 |
| Go 分配、FFI 或对象编码占主导 | 处理已定位的重复工作与分配 | 缓冲区所有权、并发生命周期、旧数据兼容 |
| 客户端调度或后台负载造成波动 | 修正测量流程并复测 | 请求分母、计划时间、完整响应、资源配置一致性 |

批量同步属于条件方案，仅在证据和剩余验证预算支持时推进。写入确认语义与现有数据格式参与兼容性验收。

定向测试覆盖本轮改动涉及的同步屏障、同键更新、提交失败、预算回滚、WATCH/通知、冷读与 TTL、生命周期、段轮换和恢复。新增测试针对具体回归风险。

### 核心矩阵

主比较使用本轮 Linux `start`、`candidate` 与 `redis` 三个版本。`candidate` 相对 `start` 的结果用于评价今晚新增收益，两者分别与 Redis 对照。

| 配置组 | 初始到达率 | 连接与数据 |
| --- | --- | --- |
| Kerniva std 与 Redis 原生 TCP、95% GET | 5,000、10,000、15,000 请求/秒 | 64 连接、100,000 key、32B value |
| Kerniva gnet 与 Redis 原生 TCP、80% GET | 1,250、2,500、3,750 请求/秒 | 64 连接、100,000 key、32B value |

每个配置每版本 6 轮，共 3 版本 × 2 配置组 × 3 到达率 × 6 轮，即 108 个正式窗口。每窗口预热 15 秒、正式测量 60 秒，测量与预热合计 135 分钟，核心阶段其余 45 分钟供填充、启动、排空和清理使用。

标定阶段可根据积压与错误调整到达率，最终参数在正式测量前冻结并记录。用于复现旧结果的固定负载另外保留。每轮三个版本使用相同请求序列和初始数据，不同轮次改变种子。六轮采用预先记录的平衡顺序，使每个版本处于第一、第二、第三位置的次数相同。

现有 Windows 运行器会对网络、读比例和到达率做笛卡尔积，且一次调用共用一个种子。新增 Linux 运行器按上述两个配置组分别调度，为 Redis 选择原生 TCP 适配，每轮显式指定种子和版本顺序。任务配置记录组、轮次、种子、引擎入口和配对身份，校验计划正式窗口总数为 108。

主评价配置在正式测量前记录，报告展示全部配置。std 与 gnet 的配置组包含不同读写比例，其结果按各自条件解释。Redis 在两组都使用自身原生 TCP 入口，各组匹配相同命令和请求条件。

正式对照期间，机器上只运行当前测量必需的进程。构建、完整测试和演示负载安排在测量窗口之外。

### Redis 正式主对照

Redis 环境与 Linux 运行器适配纳入首小时环境阶段，Redis 样本纳入 108 窗口正式核心矩阵。记录 Redis 发布版本、软件包来源或源码构建参数、二进制哈希和完整运行配置。Kerniva 与 Redis 使用同一发行版、ext4 文件系统、CPU 和内存约束、Linux 回环网络及同一压测客户端，串行执行每个窗口。

双方统一 GET/SET、键值、连接、请求序列、初始数据、到达率和成功回复时的持久化语义。主对照使用同步持久化，Redis 核对 AOF 与 `appendfsync always`、后台快照及重写策略，Kerniva 记录同步模式和维护阈值。启动前读取有效配置并核对重启恢复结果，维护事件计数与发生时刻随结果归档。

核心工作集能够完整驻留，两边采用禁止淘汰的配置并核验淘汰与内存错误计数。Kerniva 缓存预算和 Redis 内存限额分别记录其统计口径，同时展示实际进程 RSS 及 WSL 资源上限。正式窗口前完成两种引擎的相同数据填充，确保客户端、服务端和操作系统具有运行余量。

WSL 与 Redis 前置验收已经通过。后续出现环境故障时，在阶段预算内修复并重验，保留原始错误。仍有必须由用户处理的前置失败时，记录具体阻碍、已完成步骤和影响，继续完成可运行部分，并将受影响的正式对照列为未完成项。

## 8. 无人值守运行规则

### 可恢复执行

- 在 Linux 运行器中落实既有脚本的隔离目录、计划哈希、已完成窗口跳过和进程身份校验，补齐阶段级状态文件与事件日志。新旧运行器分别保存自身哈希和方法版本。
- 每个阶段记录开始结束时间、命令、退出码、标准输出和错误输出。状态文件原子替换，保存当前阶段、最近成功项、重试次数及下一步。
- 构建、测试、单个测量和进程退出各自有超时，超时计入该阶段。可恢复的环境或进程故障最多自动重试一次，使用独立的新实例。
- 进程异常后先保留数据与日志，执行恢复核查，再决定是否继续同一候选版本。
- 完成结果写入完整性标记和哈希后再作为断点。对中断窗口保存失败原因，重跑结果关联原记录。

### 分级处理

| 情况 | 自动动作 |
| --- | --- |
| 端口冲突、临时启动失败 | 更换空闲端口，保留首次错误并重试 |
| 关键正确性回归失败 | 隔离候选版本，修复后重验；到阶段上限时交付最近验收通过的版本 |
| 根因尚未确认 | 保留观测和复现，完成已有版本的对照及演示 |
| 持续过载 | 保留原负载失败记录，另建较低到达率配置完成有效对照 |
| WSL 启动或 Redis 验收失败 | 在环境预算内修复并重验，保留错误；到上限时完成可运行部分并列明三方对照的未完成前置 |
| 演示功能超出阶段预算 | 按操作、真实指标、历史查看的优先顺序交付并列明缺项 |
| 磁盘空间不足或本轮日志增长异常 | 限制新增实验，保留源码与证据，回收已核对可重建的本轮临时产物 |

### 时间与资源

- 所有阶段以 T0 的总截止时间约束，T+10:30 开始交付验收。截止前根据剩余时间决定额外窗口与重试。
- 正式实验串行执行。演示使用期间页面低频采样，正式测量时暂停演示的 INFO 轮询及客户端活动，关闭诊断插桩，仅保留冻结方法规定的资源采样。
- Linux 运行器、三个引擎构建和压测客户端使用同一 ext4 工作目录，逐窗口核对环境与构建身份。历史源码在 Linux 重建后才进入本轮比较，Windows 二进制及其结果归入历史记录。
- 实验仅使用本轮创建的数据目录。清理和终止依据绝对路径、PID、启动时刻与可执行文件身份核对。
- 本轮源码修复依据开始快照及自身差异定位，交付时保存当前实际工作区与每个被比较版本。
- 系统意外断电或睡眠会中断当前进程。阶段状态和已完成窗口支持恢复后继续执行，实际完成时长据日志说明。
