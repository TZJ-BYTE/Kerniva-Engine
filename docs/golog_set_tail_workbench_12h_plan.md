## 主线怎样定位那 1 毫秒

在 `Kerniva-Restored` 的 F 盘 ext4 上复用已验收的 gnet、同步持久化和最多 8 帧的合并同步配置。两档分别是 50% 写、3,000 请求/s，95% 读、6,000 请求/s。每窗重新建立同样的初始数据，固定种子 42、10 万个 32 字节值和 64 条 TCP 连接，预热 5 秒，测量 30 秒。DB 0 负责业务负载，DB 1 保留作跨库标记。五种配置写相同的标记，主库采样频率相同，额外命令和字节数单独计数。[现有驱动](../scripts/golog_replica_live_load.py) · [独立复算器](../scripts/golog_replica_live_compare.py)

| 配置 | 测量窗内启用的组件 | 与哪一组比较 |
| --- | --- | --- |
| A | 主库；公共轻量观测 | 提供基准。 |
| B | A 加 Rust 整理 | B−A 衡量主库独跑时加入整理的代价。 |
| C | A 加复制源和两个副本 | C−A 衡量复制源与两从整条路径的代价。 |
| D | 主库、Rust 整理、复制源、两个副本；轻量观测 | D−C 衡量存在复制时的整理代价，D−B 衡量存在整理时的复制代价。 |
| E | D 加上一轮完整观测，额外拉取封存段、轮询副本 GET 与磁盘 `CURRENT` | E−D 单独估计在完整拓扑下测量这些指标的开销。 |

每档每个配置测四次。第一时段顺序为 A–B–C–D–E、E–D–C–B–A，第二时段为 C–D–E–A–B、B–A–E–D–C。两个时段交换先跑的负载。计划共 40 个正式窗，纯测量时间 20 分钟；其余预算用于重复建库、真实追齐、跨时段对照、复验和交付。每个差值使用同负载、同轮的两个窗。用 `(D−C)−(B−A)` 检查整理与复制一起运行时是否出现额外代价。只对 E 报告高频观测支持的逐标记延迟区间。

- **负载达标。** 零失败，含排空和窗内的发送、成功四项速率都达到目标的 98%，逐秒队列无持续增长。报告每窗的真实请求数、错误数、四项速率、SET/GET p99 与 p99.9，以及客户端排队。真实过载进入结果。
- **实验有效。** 整理臂要在投递窗内看见新的快照截止序号；复制臂要看见两从推进。窗后核对所属来源、各库标记、32 个工作集样本键及应有的磁盘游标。标记从源端可取到副本读到正确值保留上下界；磁盘路径可见和目录同步完成分别表述。缺一项证据，就缩小相应结论。
- **决定下一步。** Astra 先复核 E−A 能否重现上一轮现象，再看各项差值在两个时段和正反顺序下是否同向、是否大于同配置重复窗的波动。可重复时才做针对性复验。若只有 D 同时开启两项时出现变化，按交互报告；各组来回波动则给出实测范围。只有在找到可复现缺陷、能提出单点改动并留够同口径回归时间时，才纳入本轮生产修改。同步写入的确认时机和故障恢复契约继续作为硬性验收项。

## 工作台要交付的操作

**在数据页固定一个键，重开软件后从桌面或鼠标终端点一下，就回到原连接、原库并读到它现在的值。** 这直接改善演示时反复切 DB 0、DB 1 和输入键名的问题，也适用于远程 Redis 的常用 Hash 或 Stream。

沿用当前浅色纸面、窄侧栏和五项导航。在键详情标题旁加「固定」，在「数据浏览」内提供「常用键」列表。每项显示连接、逻辑库和键名；点开后沿用现有类型详情和分页。鼠标终端提供相同的页内操作，交互命令支持列出、固定、打开和移除，切库复用已有会话接口。配置用稳定的连接 ID、逻辑库号和原始键名字节定位；打开时重新读取数据库，认证沿当前连接流程处理。[已有数据浏览与终端操作](database_workbench.md) · [桌面部署路线](workbench-deployment-plan.md)

| 验收场景 | 实际通过条件 |
| --- | --- |
| 答辩演示 | 将两个库的同名 `demo:marker` 分别固定，打开后显示不同的库和正确值。改写其中一个值，从鼠标终端打开即可读到新值；另一会话仍停在自己的库。 |
| 普通用户 | 关闭并重开工作台仍能找回位置。连接改名后仍能打开；删除连接、键过期或权限不足时显示对应状态。移除固定项后原键仍可正常读取。 |
| 多类型与边界 | 在 GUI、TUI 和交互命令之间实测空键、二进制键及至少一种分页集合。Redis Cluster 保持 DB 0，按槽读取；有精确读权限但无 SCAN 权限时仍可打开已知键。 |
| 工具交付 | 两个客户端并发固定不同键，重新打开后两项都在。独立配置检查没有保存值或密码。提供普通宽度和 393px 窄屏截图、一次包内鼠标终端实录及版本校验值。 |

## 无人值守执行约定

由 GPT‑6.2 Sol 分别负责 WSL 驱动与实测、工作台实现，独立复核者从镜像重新计算；GPT‑6.2 Astra 负责试窗放行、异常分类和最终验收。WSL 只给一位执行者持现有性能锁。桌面打包、浏览器全流程、Linux GUI 和 Redis 集群验收安排在性能锁空闲时段，避免影响同宿主尾延迟。两条线的演示实例和正式性能实例各用自己的数据目录。

启动时把 T0、截止时间、运行号、可用空间、版本与输入摘要写入账本。每窗落盘记录次序、开始结束时刻、退出码和证据路径。重连后以原截止时间继续，校验已经完成的窗，保留中断尝试。临时端口或启动失败可在新目录重试一次；若错值、来源不符或重启丢失已确认数据，暂停受影响的实验、保留现场并复现。遇到权限或平台阻塞，交付其他已验证结果。T+12 按实际完成数封存，列明未验证项。进度通知集中在启动、重要缺陷、必须人工处理的阻塞和最终交付。
