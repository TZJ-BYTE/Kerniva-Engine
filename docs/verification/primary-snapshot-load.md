# 同步 WAL 开启时，周期快照对真实读写的影响

在 WSL 的 gnet 主库上，以相同写入确认规则对比关闭和开启全量快照。8 个正式窗口共完成 2,340,000 次请求，零失败。开快照的四窗各在负载期间发布了四代，关闭时均为零。高读两组对照中，GET p99.9 在开启时均升高。

## 实验条件

服务端版本为 `9779876149e52d34ad71c3f2236495f6f2ae403e`。主库使用 ext4、同步 Go WAL、合写上限 32。64 条 TCP 连接访问 10 万个压测键，使用固定种子，两个逻辑库各有一个独立核验键。每窗预热 5 秒，正式发流 65 秒。每档按关、开、开、关的顺序跑四次，比较第 1 与第 2 窗，以及第 4 与第 3 窗。两边都把快照周期设为 15 秒，以便在短窗口内观察多次发布。产品默认周期是 300 秒。本轮没有启动外部维护器。

| 窗口 | 负载 | 全量快照 | GET p99 / p99.9（ms） | SET p99（ms） | ≥100 ms 请求 | ≥500 ms 请求 | 截止后才成功 |
|---:|---|---|---:|---:|---:|---:|---:|
| 1 | 50% 写，3,000/s | 关 | 1.262 / 1.516 | 7.438 | 0 | 0 | 2 |
| 2 | 同上 | 开 | 1.217 / 12.943 | 7.193 | 0 | 0 | 5 |
| 3 | 同上 | 开 | 147.325 / 442.499 | 182.977 | 2,376–2,378 | 97–99 | 9 |
| 4 | 同上 | 关 | 181.928 / 508.559 | 204.472 | 2,431–2,433 | 325–330 | 12 |
| 5 | 95% 读，6,000/s | 关 | 1.294 / 1.544 | 11.043 | 0 | 0 | 6 |
| 6 | 同上 | 开 | 1.327 / 6.685 | 5.702 | 0 | 0 | 2 |
| 7 | 同上 | 开 | 1.298 / 52.953 | 49.283 | 119 | 0 | 6 |
| 8 | 同上 | 关 | 1.290 / 1.499 | 5.358 | 0 | 0 | 1 |

每个高写窗完成 195,000 次请求，截止前成功速率为 2,999.82–2,999.97/s。每个高读窗完成 390,000 次，截止前成功速率为 5,999.91–5,999.98/s。延迟从请求的计划发送时刻算起，含客户端排队。阈值落在直方图桶内时列出可确定的计数范围。

高读时两组 GET p99 分别增加约 0.03 和 0.01 ms，p99.9 则从 1.544 升到 6.685 ms、从 1.499 升到 52.953 ms。高读的 SET p99 一降一升。高写第二对的两窗都出现半秒级积压，且关闭快照的一窗更多。仅凭这两对结果无法估计生产默认周期的代价，也无法把某次积压归因于快照或 GC。

第 7 窗单独复算了 119 个至少 100 ms 的请求。其中 80 个 GET、39 个 SET 全在计划秒 62–63 内。四次发布的保守区间覆盖计划秒 8–9、24、39、53–54，均与这两秒错开。最慢的 SET 为 202.276 ms，按秒桶宽度及对时误差，其计划发送时刻距最后一次发布为 7.956–9.214 秒。每秒统计没有按这个阈值细分计数，无法将 119 笔逐笔分配到两个秒桶。

## 发布与恢复

两种配置都每 250 ms 观察一次快照目录。仅统计首次看见完整代文件的时间区间完全处于正式发流窗内的发布。四个开启窗各产生四个非空文件，每个 8,989,084 字节。其各自最后一次观测到发布后，仍分别有至少 16,322、14,830、3,018、3,018 次 SET 在后续完整秒内计划发送且在截止前成功。

每窗结束都用 SIGKILL 终止主库，再从同一数据目录启动。8 次重启的两库序号、键数和核验键均与终态一致，每窗另抽验 32 个二进制值。负载对同一键反复写入相同值，抽样能验证内容，最新写入进度通过 WAL 序号增量与成功 SET 数逐窗相等验证。另有带不同值的定向用例，在快照发布后覆盖旧值并强杀，分别核验仅快照和双开时的恢复结果。[持久化开关与切换实验](persistence-modes.md)

另从第 2、6 窗各取实测期间发布的第 4 代，各自只复制这一份文件到空目录，以关闭 WAL、开启快照的配置冷启动。两次均通过真实 TCP 验证 DB 0 有 100,001 个键、DB 1 有 1 个键、两库核验键和 32 个抽样值。未加载 Rust 动态库，两次均无 WAL 目录。正常关闭只在副本生成第 5 代。原始文件的哈希、inode 和时间戳经前后复核相同。

## 验收口径与原始回执

原驱动将两边的 `INFO log_maintenance_allowed` 都预期为 `false`，最终退出码为 2。生产代码在两个持久化开关均开启时返回 `true`，表示允许外部维护器工作。本次运行的进程清单只有主库和压测客户端。保留原判定和失败回执，另从八窗的配置、进程清单、负载统计、发布时钟和恢复回执重算。按生产语义核对该字段，8/8 通过。

本机证据包 `dist/Kerniva-Go-WAL-20261126-snapshot-load-evidence.zip` 含逐窗配置、客户端统计、时钟与恢复回执、原始与修正后的驱动、独立冷读结果和 SHA-256 索引。整包 SHA-256 为 `aaea79e39203df8a4476eb9f01993463d303d351c731590d255b59f98929b799`。将包内 `workspace/` 叠加到含上述提交的检出目录，按包内 README 准备 WSL ext4 二进制目录和独占锁。在仓库根目录复跑，新结果使用独立目录。

## 快照捕获会让前台请求等多久

用来宾单调时钟分别记录申请全局执行锁、取得全局锁、取得全部库的操作锁、捕获结束、解锁和发布结束。两种程序使用相同探针，仅在周期快照成功发布后输出记录。工作负载为 95% 读、6,000/s，每窗正式测量 40 秒，每窗 240,000 个请求，并保留相同的同步 WAL 确认以及 15 秒快照周期。

原程序用一段连续数组保存每个库的快照条目，扩容时需要复制已有条目。实验版本把存活条目分块收集。两者都在锁内过滤过期键并编码值，解锁后写文件、同步数据并原子发布。实验版本的首块能容纳 32 项，此后每块能容纳 1,024 项。

| 实测顺序 | 每代捕获的存活条目 | 每窗三代的持锁上界中位数（ms） | 解锁后发布范围（ms） | GET / SET p99.9（ms） |
|---|---:|---:|---:|---:|
| 原程序 | 100,002 | 22.606 | 31.822–37.480 | 11.108 / 17.629 |
| 分块实验 | 100,002 | 11.683 | 29.169–34.175 | 1.868 / 9.241 |
| 分块实验 | 100,002 | 11.721 | 29.527–48.379 | 3.506 / 10.191 |
| 原程序 | 100,002 | 23.553 | 26.855–32.104 | 12.190 / 20.775 |

四窗共 960,000 次请求，全部成功，四次强杀恢复通过。原程序六代持锁上界为 18.724–26.678 ms，分块实验为 9.799–17.916 ms。进入全局锁后，取得各库操作锁至多用了 1.7 µs。两个反序对照均显示捕获持锁时间缩短，锁外发布没有同样的趋势。四窗均没有 ≥100 ms 请求，无法据此评估对半秒积压的影响。

### 最终实现的无探针对照

为兼顾小库，最终实现从 32 项起，块满后按 64、128、256、512 逐步增至每块最多 1,024 项。33 个存活键只需分配容量 32 和 64 的两块。空库不分配条目块，仍驻留但已过期的键也不占快照槽位。快照编码、校验、文件同步和发布顺序沿用原实现。

用没有探针的旧服务端及最终服务端重跑高读，比较方法在发流前登记。每代取覆盖发布观测区间的计划秒及前面一个完整计划秒，从中取最大的单秒 GET p99。表内的“发布附近 GET”是该窗三个最大值的中位数。它包含同期读写、客户端排队等等待，**持锁时长**见上面的单独测量。

| 高读顺序 | 发布附近 GET（ms） | 全窗 GET p99 / p99.9（ms） | 全窗 SET p99.9（ms） | 截止后才成功 |
|---|---:|---:|---:|---:|
| 旧版 | 14.647 | 1.294 / 11.010 | 13.271 | 0 |
| 最终版 | 1.974 | 1.319 / 1.679 | 8.847 | 1 |
| 最终版 | 2.851 | 1.282 / 1.634 | 8.339 | 1 |
| 旧版 | 13.238 | 1.286 / 13.107 | 51.905 | 2 |

四窗各完成 240,000 次请求，零错误，均无 ≥100 ms 请求。两对比较的发布附近指标及全窗 GET p99.9 均下降，GET p99 约为 1.3 ms。这项收益来自 10 万个键、每 15 秒一次快照的高读实测。

另以 50% 写、3,000/s 跑了旧版和最终版各一窗。每窗均有 3 代在负载期间发布，120,000 次请求全部成功，各有 3 笔在截止后完成，截止前均为 2,999.925/s。旧版窗有 148–149 次请求达到 500 ms，最终版窗为零。高写只做了一组同序保护测试，偶发积压在其他轮次也有波动，不能用这两窗估计高写尾延迟的改善幅度。

最终六窗全部通过双库强杀恢复。另把第 1 窗旧版和第 2 窗最终版在负载中发布的第 3 代文件各复制一份，分别用另一版的程序从空目录仅靠快照启动。两个方向均匹配两库的键数、核验键和 32 个二进制值，未加载 Rust，未创建 WAL。跨块、多库、空库、TTL、旧格式及校验和回归通过，Windows 数据库包测试和 WSL 快照竞态检查通过。
