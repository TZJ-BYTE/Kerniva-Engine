## 怎样区分两个进程的 GC

之前 44 个正式或复验窗口与随后 24 个诊断窗口，压测客户端的 GC 次数和累计暂停增量均为零。它们测量的是生成流量的 Go 进程。新实验对数据库主进程使用同一个冻结二进制的回环 pprof 接口，记录主库 GC 暂停、并发标记和标记辅助。隔离校准中，一次请求堆快照并要求先做 GC 的 HTTP 调用期间记录了 4 个 GC 暂停；调用前约 574 ms 的对照区间没有 GC 暂停。Go 的并发标记和全局暂停有不同的时间边界。[既有客户端记录](replica-request-stalls.md) · [Go GC 指南](https://go.dev/doc/gc-guide#Latency)

## 时间线告诉我们什么

- 异常窗的 3,749 个 GET 和 229 个 SET 分布在 64 个连接，全部在开窗后的前两个计划秒内发起调度。跨进程比对使用同一来宾的单调时钟，客户端测量起点保留 74.690 ms 的因果区间。即使取最不利端点，第一次主库 GC 暂停仍比最后一个慢请求完成至少晚 **6.086 秒**。该窗 3 段并发标记与 3 段标记辅助均完整记录，均未与这些慢请求重叠。此判断直接适用于这次捕获。历史异常窗缺少同等服务端跟踪。
- 在 64 个连接各自最先达到阈值的请求中，61 个从发起网络交换到收到完整回复至少用了 100 ms。随后，整批慢请求中有 **3,874** 个在客户端发送前就已经等了至少 100 ms。单条请求可能同时在两段都慢。第一段交换时间包含客户端调度、网络及服务端处理。
- 同一份主库跟踪可以定位经过 `Writer.writeFramesLocked → File.Sync → syscall.Fsync` 的日志同步调用。按保守时钟区间，仅计入明确完整落入指定时段的调用，异常窗开头 1.2 秒有 **30/70** 次至少 10 ms，其中 **4** 次至少 50 ms。相邻正常跟踪窗相同时段为 **1/315** 次至少 10 ms、**0** 次至少 50 ms。两窗余下 1.2–30 秒均无达 10 ms 的完整日志同步。最长一次为 **56.110 ms**，与至少 13 个慢 SET 的交换区间重叠，其中一条至少重叠 **49.280 ms**。这些是 Go 运行时观察到的系统调用区间，包含可能的调度和存储等待。[两窗同步时长](primary-fsync-windows.json)

本次记录缺少请求序号到写入批次的映射。后续已在新的自然尖峰中按连接内序号对齐真实批次，并用独立 TCP 连接验证了慢同步如何通过监控命令的全局锁影响其他库。[后续定位与修复对照](observer-execution-gate.md)
