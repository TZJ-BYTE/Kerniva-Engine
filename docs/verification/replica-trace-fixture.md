# 已知慢回复与后继排队的验证

2026-11-26，北京时间 08:03。前一轮开启逐请求探针的 12 个数据库窗口中，没有一条请求达到 100 ms。本实验用隔离的回环 RESP 测试服务验证慢请求记录与回放路径。[前一轮自然流量结果](replica-request-stalls.md)

冻结的 Linux 压测客户端以单连接、每秒 100 个 SET 连续发 3 秒。三次运行各有独立的服务进程、连接和端口。第一次立即返回全部正确回复；后两次各只将索引 50 的成功回复延迟 250 ms。索引从 0 开始。测试服务记录收齐请求、开始回包和回包完成的单调时钟，客户端记录自己的四个时间点。两端依单连接命令序号配对。

| 同一条请求的时间 | 无注入对照 | 注入一 | 注入二 |
| --- | ---: | ---: | ---: |
| 服务端收到第 50 条至开始回包 | 0.007 ms | 250.164 ms | 250.475 ms |
| 第 50 条客户端发前排队 | — | 0.901 ms | 1.067 ms |
| 第 50 条发起网络交换至完整回复 | — | 250.345 ms | 250.722 ms |
| 紧邻第 51 条客户端发前排队 | — | 241.254 ms | 241.800 ms |
| 第 51 条发起网络交换至完整回复 | — | 0.061 ms | 0.096 ms |
| 总耗时至少 100 ms 的请求 | 0 | 16 | 16 |

对照中的第 50、51 条既未进入固定哈希样本，也未触发慢记录，因此表格用空栏表示。三次共核对 900 个 SET 的命令、键、32 字节值及正确回复，零失败、零丢样。两次注入的慢请求均为索引 50 至 65，全部保留。客户端都观察到第 51 条的计划发出时间落在第 50 条尚在等待完整回复的区间。

这项验收证明当前工具可以区分先发请求等回包、后继请求积压这两种情况。业务数据库的自然尖峰起因仍待真实慢请求与对应服务端操作的联合记录。[逐请求原始时长、样本覆盖与输入哈希](replica-trace-fixture.json)
