# 同步写入变慢后，排队需要多久才能消退？

### 一笔 805 ms 的 SET 如何排队

对现行版本按相同高写配置再运行一个 125 秒窗口。两端只扩大诊断记录容量，同时采集 WSL 内核事件。375,000 条请求全部成功，GET / SET p99 为 2.07 / 24.18 ms。187,342 个成功 SET 均按 TCP 连接和请求序号匹配到服务端记录。两端应用跟踪和 32 个 CPU 的内核缓冲均未丢记录。

最慢的 SET 是连接端口 38504 上的第 2002 个请求，从计划投递到完整回复共 **805.303 ms**。前两行分别给出发送前和发送后的耗时，第三行追溯占用同一连接的一笔写入。

### 写者还可以多合并多少已经到来的请求

沿第 2002 笔请求往前看，将七笔前序 SET 的服务端时间裁剪到它们实际占用连接的 771.478 ms 内。其中 **572.092 ms** 从前序请求开始尝试提交给 WAL 写者算到写者完成取批，包含等待写者同步其他批次的时间。另有 **194.876–194.884 ms** 花在它们各自所在批次的磁盘同步，其余约 4.50 ms。第 1995 笔只有在目标请求计划投递之后的部分计入。计算使用连接内的发送、回复顺序和 8.515 µs 的跨进程相对时钟区间。

同一诊断窗有 423 个 GET、526 个 SET 用时至少 500 ms。它们从计划投递到完成所跨的区间里，写者取了 75 批，全部取满 16 条。每批取完至少 1 ms 前，另有至少 16 个最终写入同一日志段的 SET 已到达入队代码。记录点位于向通道发送之前，无法由此确定每批当时还能立即取走几条。另一组确定性测试在第一个同步调用处阻塞写者，将后续 33 条写入逐条放入通道，再放行。上限设为 32 的写者实际合并 32 条，留 1 条待取。在第二次同步被阻塞时，等待的 33 条均未提前返回。让这次同步失败时，整批 32 条都报错，回滚后剩余 1 条正常提交。成功和失败两条路径均按原始帧字节、序号和 Rust 重启读值核对。Windows、WSL 的竞态检测各重复三次通过。

再按 500 ms 门槛复算旧原生高写窗的原始直方图。97,293 个成功 SET 中有 324–327 个达到 500 ms，最长 707.283 ms。这批慢写的计划投递时刻同在第 45 秒，该秒 SET 的最大发送前排队为 664.745 ms。两项最大值来自分别汇总的指标，无法直接相减来估算某一笔的服务耗时。原生 Windows 的结果足以说明半秒慢写在没有 WSL 的情况下也会发生。

### 移除数据库后的同步写对照

另以同一份独立 Go 程序依次在 Windows、WSL、WSL、Windows 运行。每窗向同一数据盘上的一个新文件追加 15,000 笔 257 字节数据，计划每 2 ms 一笔，每笔立即调用 `File.Sync`。程序是单线程写入，记录计划时间、实际开始、开始同步和同步结束。四窗共 60,000 次均成功。

| 顺序 | 单次同步中位数（ms） | 单次同步最大值（ms） | 实际开始距计划的最大延误（ms） | 开始前已落后计划 ≥500 ms（次） |
|---|---:|---:|---:|---:|
| Windows | 0.582 | 14.970 | 1,473.363 | 2,005 |
| WSL | 1.570 | 22.704 | 43.322 | 0 |
| WSL | 1.627 | 18.656 | 47.385 | 0 |
| Windows | 0.565 | 6.161 | 4.896 | 0 |

首个 Windows 窗口的前四个计划秒内，每秒的同步中位数为 2.30–2.52 ms，持续高于 2 ms 的计划间隔，后续写入逐步落后。最长一次开始前已等 1.473 秒，单次同步最长只有 14.97 ms。该窗口展示了无数据库代码时形成积压的一种机制。独立程序每写一次就同步，服务端则分组合写；无法由此确定原先某个 SET 的触发原因。四窗均无一次文件同步达到 50 ms。

本次对照固定了源码、编译器、物理盘和流量。要进一步单独估计 WSL 虚拟化开销，可在同一台机器、同一块 SSD 的原生 Linux ext4 上运行相同 Linux 二进制与相同负载，与 WSL ext4 交叉比较，并对齐实际合批、来宾同步时间和客户端排队。部署顺序及数据目录要独立，保留正常同步写确认。

### Windows 原生单笔同步写的内核时间线

在 F 盘同一块 NVMe SSD 上保留上节的 257 字节、每秒 500 笔和每窗 15,000 笔。A 使用上一轮的原始二进制。B 把写循环固定在一个 Windows 线程，记录 PID、TID 以及每次 `File.Sync` 前后的高精度计数器（QPC）。先在关闭内核录制时按 A、B、B、A 交叉运行。四窗共 60,000 笔全部成功，Go 时钟测得的单次同步最大值依次为 6.073、17.128、6.972、6.513 ms。B 增加了锁线程和计时调用，两种探针均保留用于复验。

随后在独立的 30 秒窗口用 Windows Performance Recorder 同时记录目标文件、磁盘刷新与线程调度。15,000 笔全部成功，其中 14,999 笔在计划的 30 秒内完成，最后一笔在 30,001.17 ms 完成。全部 15,000 次调用均与指定文件、进程、线程和同一文件层请求的成功完成事件逐笔配对。整份 ETL 处理了 4,525,311 条事件，记录的事件和缓冲区丢失数均为零。

| 本窗指标 | 中位数 | p99 | 最大 |
|---|---:|---:|---:|
| 单次同步的 QPC 耗时 | 0.724 ms | 1.448 ms | 11.854 ms |
| 每次同步内可明确配对的线程就绪到运行时间之和 | 0.0065 ms | 0.4031 ms | 8.2748 ms |
| 实际开始写入距计划时间的延迟 | 0.508 ms | 1.649 ms | 13.118 ms |

最长的是第 3,627 笔。它进入文件层刷新后 11.8391 ms 收到成功完成事件。以进入 `File.Sync` 为零点，同线程对磁盘 1 发起的一次刷新从 +2.9238 ms 持续到 +11.8268 ms。写线程在 +3.5454 ms 已经就绪，到 +11.8178 ms 才获得 CPU。两个区间重叠，直接相加会重复计算。文件层和磁盘层分别使用不同的请求标识，磁盘事件依靠发起线程、目标物理盘和时间重叠关联。线程就绪证据说明这笔调用中实际发生了调度等待，判定整机 CPU 饱和还需要其他同时段证据。历史 1.473 秒积压发生在另一窗口，两次测量不能跨窗口拼接。
