# 同步写入变慢后，排队需要多久才能消退？

在 WSL ext4 上，主库启用 gnet、增量日志和同步确认。64 个 TCP 客户端访问相同的 10 万个键，预热 5 秒，然后按固定速率连续投递 65 秒。限时包括等待空闲连接的时间。下表的成功速率只计截止时已回完的请求，失败数计入排空期间的最终结果。GET 和 SET 的 p99 均从计划发送算到收到成功回复；超时另外计数。两档负载分别是 50% 写、每秒 3,000 次和 95% 读、每秒 6,000 次。

## 多等一会儿合并写入

实验版在两个 SET 已就绪时最多再等 600 微秒，以期让第三条也共用一次同步。30 秒初筛减少了约 11% 的同步次数，低负载时 SET 中位延迟增加约 0.23 ms。延长负载并把两个版本的次序颠倒，改动带来的尾延迟改善没有重现。以下窗口均关闭了客户端和服务端的逐请求跟踪。

| 负载 | 投递顺序 | 最终失败数 | 截止成功数/s | GET p99（ms） | SET p99（ms） |
|---|---|---:|---:|---:|---:|
| 50% 写 | 原版 | 1,178 | 2,938.3 | 1,551.9 | 1,581.3 |
| 50% 写 | 等候 | 0 | 3,000.0 | 497.0 | 529.5 |
| 50% 写 | 等候 | 3,986 | 2,904.3 | 1,757.4 | 1,786.8 |
| 50% 写 | 原版 | 0 | 2,999.8 | 504.4 | 555.7 |
| 95% 读 | 等候 | 0 | 6,000.0 | 1.33 | 11.96 |
| 95% 读 | 原版 | 0 | 5,997.2 | 1.36 | 23.00 |
| 95% 读 | 原版 | 0 | 5,999.9 | 1.28 | 5.73 |
| 95% 读 | 等候 | 0 | 5,999.9 | 1.28 | 5.85 |

首窗客户端统计有 26 个已发出的 SET 等待回复超时。服务端序号增量为 96,734，客户端成功 SET 为 96,708，相差 26。客户端超时后不能据此断定这条写入没有提交。

## 高写时临时打开 2 ms 合写窗口

本轮保持 WAL 格式、每批最多 8 条和原有同步确认。候选在连续两个 250 ms 观测区间达到高写入速率后开启等待，低于退出阈值后恢复原策略。每批以首个排队请求为起点最多等待 2 ms，已经凑满一批就立即写盘。每个窗口都用真实 gnet 连接。

|---|---|---:|---:|---:|---:|
| 50% 写，3,000/s | 原版 | 279 | 3,048 | 1,388.3 | 1,434.5 |
| 50% 写，3,000/s | 自适应 | 0 | 4 | 512.8 | 551.6 |
| 50% 写，3,000/s | 自适应 | 0 | 5 | 1.21 | 6.46 |
| 50% 写，3,000/s | 原版 | 0 | 2,672 | 1,098.9 | 1,132.5 |
| 95% 读，6,000/s | 原版 | 0 | 6 | 1.25 | 8.13 |
| 95% 读，6,000/s | 自适应 | 0 | 1 | 1.26 | 4.92 |

两个高写候选窗各完成 195,000 个请求，每千笔 WAL 提交的同步次数分别减少 33.52% 和 32.05%。第一窗仍有 9,929–9,942 个成功 SET 达到 100 ms，第二窗为零。65 秒对照证实了同步次数下降，重复运行时的尾延迟尚有较大波动。原始窗及摘要在 `logs/golog-adaptive-crossover-20261126`。

在另一组受控实验中，每窗选中一次成功的真实磁盘同步，在成功返回之后、唤醒等待者之前额外暂停约 300 ms。四窗的服务端队列峰值均在 60–63 条，客户端计划到期但尚未发出的请求峰值分别为 793、1,633、1,783 和 2,894。每批上限按 8、16、16、8 运行，恢复后首次满足排空判据的 100 ms 时间桶依次出现在 200、1,500、1,600 和 2,000 ms。扩大上限对消退时间的影响未在两对中复现。注入时刻、实际暂停、直方图和逐笔记录位于 `logs/golog-single-sync-pulse-prepared-20261126/run-20261126T073807Z`。

## 同一程序每批最多合并 8 条或 16 条

服务端和客户端都使用同一套二进制，唯一变化是 `go_log_group_max`。两种上限都只取已经在队列中的写入，一次磁盘同步完成后才确认整批。表中截止缺口包括已失败和截止时仍未收到回复的请求。

| 负载 | 合写上限 | 最终失败 | 截止缺口 | GET p99（ms） | SET p99（ms） |
|---|---:|---:|---:|---:|---:|
| 50% 写，3,000/s | 8 | 1,573 | 3,967 | 1,493.17 | 1,522.53 |
| 50% 写，3,000/s | 16 | 0 | 13 | 274.73 | 307.23 |
| 50% 写，3,000/s | 16 | 0 | 3 | 256.90 | 318.77 |

每对高写测试中，16 条上限的 GET 和 SET p99 都较低，但两个窗口仍分别有 1,454 和 1,472 个成功 SET 达到 100 ms。高读四窗没有请求达到 100 ms，16 条上限的 SET p99 在两对中分别增加 0.61 和 0.57 ms。示例配置仍用 8。逐秒数据和原始直方图位于 `logs/golog-group16-20261126/paired-20261126T070321Z`。

预分配和合写上限的 16 个窗口各记录到一次**客户端** GC，单窗的 GC 暂停总计 0.099–0.326 ms。观察到的百毫秒至秒级延迟远长于这些暂停。针对**服务端**，另一轮已将 3,978 个慢请求与 GC 时序逐条核对，首次全局暂停发生在它们全部结束至少 6.086 秒后。[主库 GC 与请求时间线](primary-gc-stalls.md)

## 区分文件扩展与数据同步开销

另用同一 ext4 设备上的 8 个文件，每臂做 9,000 次 257 字节顺序写入，每次写后同步。固定长度文件先用零完整写过并同步，测量只覆盖现有数据块。每臂使用同一数据和计划到达时间，两轮反转顺序。下面只比较调用本身的耗时和实际完成速率。

| 文件布局及屏障 | 两轮同步 p50（ms） | 两轮同步 p99（ms） | 两轮完成次数/s |
|---|---|---|---|
| 逐次扩展、`fsync` | 1.55 / 1.69 | 3.27 / 4.31 | 610 / 540 |
| 定长覆盖、`fsync` | 0.79 / 0.80 | 2.47 / 2.55 | 978 / 923 |
| 逐次扩展、`fdatasync` | 1.55 / 1.52 | 3.44 / 3.55 | 606 / 615 |
| 定长覆盖、`fdatasync` | 0.73 / 0.72 | 2.06 / 1.73 | 1,182 / 1,269 |

相同 `fsync` 下，覆盖已写过的定长文件，两轮都更快。八个单写窗口都未达到计划的每秒 1,500 次写入。主库按批同步，不能用这些数推算服务吞吐。定长日志还需要在崩溃后可靠识别最后一次有效提交。

把定长写入接到隔离的主库原型后，结果也经过反序检验。原型用两个校验过的提交描述符记录有效末尾，每批仍调用一次 `File.Sync`。两个高写对中，原版 → 定长的 SET p99 为 1,078 → 502 ms，反序定长 → 原版则为 1,674 → 579 ms。第二个定长窗失败 1,968 次，截止缺口 4,870 / 195,000。高读四窗均零失败，定长 SET p99 分别为 11.01 和 4.70 ms，两侧原版分别为 4.80 和 4.96 ms。因此未启用该文件格式。进程强杀和校验损坏用例通过，真实掉电、磁盘写满时的格式转换仍有恢复限制。每个新活动文件还会占用约 4 MiB。

## 一笔慢写在虚拟磁盘上等了什么

在一次 50% 写、3,000/s 真实负载中，关闭前段内核采集后再开启窄范围跟踪。截取的 30.769 秒含 1,325,810 个来宾内核事件，环形缓冲没有覆盖或丢弃。对能核准 DB 0 活动日志文件描述符、设备、inode 和写线程的慢批次，按客户端与服务端的独立时钟界限双向检查唯一匹配。下面两笔在较宽的原始时钟界限内均可唯一定位。按前、后半段重新匹配系统调用时，分别有 4,955/4,955 和 4,906/4,955 笔支持同一偏移，重合区间宽 1,041 ns。

| 批次与 ext4 同步入口时间 | Go 同步 / 内核 fsync（ms） | 写线程等待写回 / 等待 ext4 日志提交（ms） | 等待区间内两次虚拟 SCSI 刷新（ms） |
|---|---:|---:|---:|
| 24983，投递第 38.576–38.586 秒，8 帧 | 55.630 / 55.603 | 16.894 / 38.646 | 15.429 + 22.720 |
| 33828，第 66.557–66.567 秒，排空阶段，1 帧 | 46.560 / 46.544 | 0.225 / 46.272 | 8.602 + 37.278 |

这两笔中，每条 `SYNCHRONIZE CACHE` 的起止与同一来宾设备上唯一一对块层 flush 在 2 µs 内吻合。共筛出的 20 个慢样本都在日志等待区间内出现两次成功的虚拟缓存刷新，其中 19 个紧邻同一次积压，不能看成 20 次独立复现。40 条指令中有 31 条能唯一对应块层 flush。没有贯穿文件系统、SCSI 与宿主物理 SSD 的共同请求编号。

按计划发送秒分桶，第 37 秒 GET / SET 的客户端排队 p99 均为 1.09 ms，第 38 秒升至 887 / 891 ms，第 40 秒回到约 1.1 ms。这段时间有多次 30–55 ms 的同步。该证据定位到了实际发生的磁盘等待，也保留了单次同步和整条队列的区别。复算文件 `logs/golog-coalesce-20261126/scsi-narrow-recalibrated.json` 的 SHA-256 为 `5d69cc141f34b4a7a444c9a027b7b163ee8f5a92f9f79504ad2f62a169ef8a31`。

## Windows 原生部署

在存放 WSL 虚拟磁盘的同一物理 SSD 上，另用原生 Windows 主库和 F 盘 NTFS 目录运行同一负载。两窗均启用同步日志、关闭主库快照，沿用上限为 8 的合写。每窗结束后强制终止自己的主库进程，再核对序号、键数、覆盖与删除，两个实例均恢复成功并可继续写入。

| 负载 | 最终成功 | 截止前成功 | GET / SET p99（ms） | GET / SET ≥100 ms（次） |
|---|---:|---:|---|---|
| 50% 写，3,000/s | 195,000 | 194,997 | 186.65 / 220.73 | 1,173 / 1,306–1,309 |
| 95% 读，6,000/s | 390,000 | 389,997 | 0.84 / 5.29 | 0 / 0 |

高写窗的慢请求在 Windows 原生环境也出现了。两种部署同时改变了文件系统、操作系统和 I/O 路径，各档只做了一个原生窗口。仅凭这些数无法把问题归给某一块硬件、WSL 或 Go GC。100 ms 位于一个直方图桶内，因此报告能从原始桶确定的上下界。

## 复现与核验

两组 WSL 代码候选都从同一份已冻结的服务端源码构建。完整的实验脚本、配置、候选补丁、客户端原始统计和摘要保存在 `Kerniva-Go-WAL-performance-20261126-evidence.zip`。其 SHA-256 为 `993b1d8c84d16dd793d97002b4b6271866b197222da2b225bc791978bfa35de7`。包内 `README` 和 `verify.py` 说明了核验步骤，9 份大于 16 MiB 的原始跟踪以完整哈希和留存位置索引。各微实验原始 CSV 已随包提供。

Windows 对照可在仓库根目录用下列命令重跑。将二进制路径替换为实际构建产物，`--scratch-parent` 选取待测 NTFS 卷上的现有目录，`--output` 每次使用新目录名。省略 `--execute` 可以先检查参数、记录二进制哈希。[Windows 原生采集脚本](../../scripts/golog_windows_native_load.py)

```powershell
python -B scripts/golog_windows_native_load.py --server bin/kerniva-server.exe `
  --bench bin/kerniva-bench.exe --library bin/kerniva_engine.dll `
  --scratch-parent F:/ --output logs/native-gnet-repeat-01 --execute
```
