# 269.653 ms 的日志同步花在了哪里

2026-11-26，修复跨库监控阻塞后的 WSL 单主在真实 gnet 流量下再次出现长尾。最长一笔 SET 从发出到收齐回复用了 635.784 ms，其中在服务端写队列等了 365.817 ms，随后所在批次同步用了 269.653 ms。对应的 Linux 写线程在 `ext4_sync_file` 内经历三段不可中断睡眠，合计 269.593 ms。它被唤醒后，等到重新获得 CPU 合计只用了 0.030 ms。这次同步的耗时已经定位到来宾内核，物理盘、虚拟盘和文件系统日志各自贡献的时间仍待区分。[上轮 Windows 与 WSL 磁盘计数实验](primary-host-disk.md)

## 四个正式窗口

同一组冻结二进制，10 万个小键、64 条 TCP 连接、95% GET、目标 6,000 请求/s。每窗预热 5 秒，正式投递 30 秒。Go 主库使用 strong/sync，合并上限为 8。下表的开关只控制来宾内核跟踪。延迟从计划发送计至收齐回复。四窗共 720,000 次请求，零失败，35,536 条 SET 均与服务端批次核对成功。

| 窗口 | 内核跟踪 | GET p99（ms） | SET p99（ms） | ≥100 ms 的 GET / SET | 最长 Go 同步（ms） |
|---|---|---:|---:|---:|---:|
| 1 | 关 | 1.311 | 6.046 | 0 / 0 | 11.187 |
| 2 | 开 | 1.307 | 6.111 | 0 / 0 | 10.355 |
| 3 | 开 | 253.231 | 429.916 | 2,664 / 216 | 269.653 |
| 4 | 关 | 91.750 | 224.395 | 1,602 / 242 | 116.738 |

两个开关状态都复现过请求长尾。四窗按固定顺序采集，不能据此估算跟踪对尖峰概率的影响。此前主机磁盘采样实验的八窗与本轮四窗共同覆盖 216 万次正式请求，全部成功；两组中的尖峰发生在不同时间。

## 两种已知条件下的单写对照

两次均启动真实主库，只测一条 DB 0 SET，同时核对其活动日志、Go 批次和内核写线程。第二次用 strace 将 fsync 返回延迟 220 ms。借助两端时钟界限，可以区分停顿发生在内核调用内还是返回后。

| 单写条件 | Go 同步（ms） | 内核 fsync（ms） | D 状态（ms） | 唤醒后等 CPU（µs） | 调用外时间 |
|---|---:|---:|---:|---:|---:|
| 普通 SET | 3.733 | 3.729 | 2.908 | 9 | 2.675–4.673 µs |
| fsync 返回延迟 220 ms | 223.167 | 2.862 | 2.819 | 3 | 220.303727–220.305725 ms |

注入对照中，至少 220.070983 ms 发生在内核调用返回后。在正式负载前另有一个 5 秒烟测，30,000 次请求全部成功，1,372 个测量批次均有唯一调用时序，其中 1,308 个通过活动日志身份核验。

## 如何核对同一条写入

1. 从 TCP 源端口、连接内请求序号和服务端写记录定位 SET 所在批次。按 Go 批次的同步边界与来宾单调时钟的区间，筛选可能的内核调用。多批次窗口分前后两半，各半至少 90% 的批次须支持共同的偏移范围，最终匹配必须唯一且顺序一致。90% 是校时的覆盖门槛。
2. 对上表六个慢调用做反向核对。只用原始校时界限，保留约 8–9 ms 的不确定性，在服务端所有已记录批次中寻找能完整容纳该调用的批次，范围包含非压测连接。六次都只能对应表中的那一个批次。已知延迟对照同样只有一个候选。另从内核端枚举所有 ≥10 ms 的 fsync，第 3 窗还找到一笔 266.523 ms，时序唯一对应非压测连接的一条 SET（批次 1373）。该调用缺少 DB 0 活动日志身份凭据，单独保留。
3. 核对系统调用的 fd、ext4 进出的设备和 inode，再与主库打开的 DB 0 活动日志比对。采集器约每 80 ms 检查一次，记录身份变动的前后观测。轮转附近无法确认的批次单列。内核文本以 1 µs 为单位舍入，时间界限按每个端点 −500 至 +499 ns 展开。[Linux ftrace 的时间舍入实现](https://github.com/torvalds/linux/blob/v6.18/kernel/trace/trace.c#L357)
4. 把同一个写线程在调用内的切出、唤醒、切入与 ext4 事件对齐。丢失唤醒或无法闭合的轨迹标为不完整。块设备事件只提供同一时间段的背景，其格式缺少把单个 flush 唯一分配给某个批次的标识。

| 内核窗口 | 测量批次 | 唯一时序匹配 | 通过活动日志核验 | 其中调度记录完整 | 无唯一时序的批次 |
|---|---:|---:|---:|---:|---|
| 2 | 7,978 | 7,869 | 7,409 | 7,388 | 109 个缺少候选 |
| 3 | 7,826 | 7,825 | 7,399 | 7,378 | 1 个有两个候选 |

跟踪使用独立的 tracefs 实例，两个正式窗的内核缓冲区均记录零丢弃。各窗在初始线程枚举后都新增了一个未进入过滤集合的 OS 线程。第 2 窗的 109 个缺口均在新线程出现后；这些批次实际运行在哪个线程仍无法逐笔确认。四个正式窗均已退出并完成进程和端口检查。

## 下一步怎样区分等待来源

本机已核实支持按设备和事务编号记录 JBD2 文件系统日志的提交阶段，也能在指定线程因 D 状态切出时取得内核调用栈。下一次先用单写夹具核对采集开销、运行栈和日志轮转，再用相同负载检验长同步的写者是否停在等待日志提交的函数。要把停顿归到某一个事务，需同时取得写者等待的事务编号和该事务的提交起止记录。仅时间重叠时将单独列出。随后用同一耐久级别做前后配对，检验候选改动对 95% 读尾延迟和 50% 写吞吐的影响。

## 重放与再次采集

本地证据包为 `dist/Kerniva-kernel-writer-20261126-evidence.zip`，旁有同名 `.sha256`。包内保留两个正式跟踪窗的完整内核文本、每窗客户端请求与 Go 服务端批次、采集回执和正式采集器源码快照。解压后在解压根目录执行下列 PowerShell 命令即可离线重放，需要 Python 3.11 或更新版本。

封包时分别从原始 WSL ext4 和 Windows 镜像重读了 100 个原始文件，SHA-256 全部一致。压缩包为 46,304,048 字节，SHA-256 为 `8cda5ee45dfa17fbc29e918abf631bfdb36a7c1b4ba8e879894b496ae4b3ee70`。在解压目录重放以下四组分析后，输出与包内结果逐字节相同。

```powershell
$raw = 'logs/golog-kernel-writer-20261126'
foreach ($stage in 'single','single-delay','smoke','natural') {
    python -B scripts/golog_kernel_writer_report.py --raw "$raw/$stage" --out "$raw/$stage-replay.json"
    if ($LASTEXITCODE -ne 0) { throw "重放失败 $stage" }
}
```

在保存有同一组冻结二进制和校验清单的 WSL 环境，可从仓库根目录再次采集。普通用户运行主库和压测，辅助进程通过 `wsl.exe` 以 root 创建有时限的私有 tracefs 实例，退出时销毁。新运行使用全新的输出目录。自然尖峰出现的时间和大小会随实际负载变化。

```bash
setup=logs/set-tail-stalls-20261126/setup.json
bin=/home/lemon/kerniva-ping-build.793ihwSZ/Cbin
manifest=logs/golog-batch-20261126/reviews/ping-gate/C-binaries.sha256
out=$(mktemp -d -p logs kernel-writer.XXXXXXXX)
for stage in single single-delay smoke natural; do
  python3 -B scripts/golog_kernel_writer_capture.py --setup "$setup" --bin "$bin" \
    --binary-manifest "$manifest" --mirror "$out/$stage" --stage "$stage" || exit 1
done
```
