# 毕设设计说明

## 研究问题

建议题目为《面向小键值混合读写负载的内存数据库读延迟优化设计与实现》。

数据库需要把写入同步到硬盘后才回复成功。一次同步变慢时，无关 key 的缓存读取仍应具备独立完成的机会。本课题研究这条等待链，关注 GET 的 p99、SET 的确认延迟、内存开销和一致性。

核心实验使用小字符串、同步持久化、GET/SET 混合访问和能够完整缓存的数据集。需要分别分析异分片缓存命中、同分片争用、冷读和带 TTL 数据。

## 现有系统如何工作

~~~mermaid
flowchart LR
    C[RESP 客户端] --> N[Go std 或 gnet 网络入口]
    N --> Q[每连接有界命令队列]
    Q --> E[命令执行门]
    E --> D[Go 数据库与分片缓存]
    D --> F[Go 到 Rust 的 C ABI 桥接]
    F --> R[Rust 追加日志与已提交索引]
    R --> S[segment 文件与 checkpoint]
~~~

Go 负责协议、命令、字符串与复杂数据类型、TTL、事务执行隔离、WATCH 版本、缓存预算和客户端生命周期。Rust 负责追加记录、原子批次、文件同步、索引、恢复、快照和旧段回收。

Go 缓存保存解码后的 DataValue。Rust 用 BTreeMap 保存 key 到日志位置的映射，value 存放在 segment 中。读取缓存未命中时，经 Rust 定位读取、校验 checksum，再解码进入缓存。

2026-11-15 第一轮实验保存的最早基线中，持久化命令持有数据库级排他锁。Rust 也在一个状态写锁内完成追加、同步和索引发布。因此硬盘等待同时进入 Go 缓存读路径和 Rust 冷读路径。第一轮已完成 Go 分片热操作路径及 Rust writer/index 拆分，2026-11-17 在这个起点上继续缩小 Go 的等待范围。

## Go 的提交与发布

普通 SET 的并发路径首先取得数据库生命周期读锁，再短暂取得目标分片的热操作写锁。该路径用于已缓存、存活、无 TTL 的字符串，要求策略为 noeviction，并且能够预留暂存预算。

每个分片保存正在提交的 key 及其完成通知。写入准备好私有值后，登记该 key，再释放分片锁执行 Rust 提交。同 key 的 GET/SET 释放分片锁并等待通知，醒来后重新检查状态。其他 key 可以取得分片锁继续执行。提交完成后重新取得分片锁，完成缓存、WATCH 与预算发布，再移除登记并唤醒等待者。生命周期读锁覆盖整个过程，使 Clear/Close 能够等待所有在途操作结束。

~~~mermaid
sequenceDiagram
    participant W as SET 写请求
    participant G as Go 缓存
    participant R as Rust 提交
    participant Q as 同分片其他 key 的 GET
    W->>G: 锁定目标分片并预留预算
    W->>W: 复制私有新值并序列化
    W->>G: 登记本 key 的提交通知并释放分片锁
    W->>R: WriteBatch
    R->>R: append 与文件同步
    Q->>G: 取得分片锁并读取已提交缓存
    G-->>Q: 返回独立副本
    R-->>W: 提交成功
    W->>G: 重新取得分片锁
    W->>G: 发布新缓存值
    W->>G: 更新 WATCH 版本与变更通知
    W->>W: 结算暂存预算
    W->>G: 移除提交登记并唤醒本 key 等待者
    W-->>W: 返回成功
~~~

暂存值属于单个操作。提交期间，旧缓存条目继续代表已提交状态。失败只释放该操作的预算，版本与通知在实际提交后发布。异分片的提交互相独立结算内存，避免一个失败操作覆盖另一个成功操作的统计。

同 key 的 GET/SET 在缓存发布完成前等待该 key 的提交通知。返回成功之后的读取能够看到新值。GET 返回独立副本，输入 key 与 value 在跨调用保存时拥有自己的存储。每次持久化 SET 增加一个完成通知，GET 增加一次正在提交 key 的 map 查询，其分配与内存成本参与实验评价。

暂存预算沿用项目现有的近似 payload 统计口径，包含待发布值和保守的序列化空间估计。Go map、对象头、Rust 索引与运行时分配仍需要额外内存。`used_memory_bytes` 已包含在途预留，`pending_memory_bytes` 是其中的暂存分项，两项相加会重复统计。暂存分项通过 Database.GetStats 与回归测试核查，稳定状态下应归零，当前 INFO 尚未输出该分项。

### 全局协调入口

缺失 key、冷读、带 TTL 的值、类型转换、预算不足、其他淘汰策略以及复杂命令使用现有排他协调。切换时先释放分片锁与生命周期读锁，再取得排他锁并重新检查数据。

带 TTL 的值始终进入协调路径，覆盖入口检查后跨越到期时刻的情况。此时过期删除、持久化 tombstone 和版本变更参加同一个协调过程。

Go RWMutex 有写者排队时会阻止新读者进入。周期 TTL 扫描依次尝试执行门的 TryRLock 和数据库的 TryLock，忙时延至下个周期，避免扫描排队导致无关热读一起等待。持续繁忙期间需要观察物理清理进度和内存占用，逻辑过期仍在访问路径检查。[Go 同步原语文档](https://pkg.go.dev/sync#RWMutex)

扫描器的 Start、Stop 与 Close 通过 expireMu 串行协调。Close 先禁止再次启动扫描器，停止并等待当前 worker 结束，再取得数据库排他锁关闭存储，避免 WaitGroup 注册与停止等待交错。

复杂命令、到期访问、冷读回退和 Close 等排他操作仍可形成全局等待。性能报告需要包含这些边界下的测量。

## Rust 的写入状态与已提交索引

Rust 将两个职责拆开。

| 状态 | 保护方式 | 内容 |
| --- | --- | --- |
| 写入状态 | writer Mutex | active file、段编号、追加位置、同步、截断回滚、checkpoint 计数和错误状态 |
| 已提交索引 | index RwLock | key 到已发布 ValueLocation 的映射 |

写者串行执行追加与同步，成功后短暂取得索引写锁发布位置。WriteBatch 在同一次索引写锁持有期间发布全部子操作。Clear 在 marker 提交后切换为空索引。

GET 取得索引读锁，查找位置，并在该锁内取得独立 OS 文件句柄。随后释放索引锁，执行定位读取与 checksum 校验。GET 的这条路径可以绕过写者的同步等待。

上述能力由 Rust 直接 API 的冷读屏障验证。完整 RESP 服务的冷 GET 仍取得 Go 数据库排他锁，会排在在途 SET 之后，并通过写者排队阻止该库后续热 GET 进入。

锁顺序遵循 writer 到 index。普通读取只进入 index 和 reader cache。snapshot 在索引读锁内复制位置并登记 segment pin，保证 cleaner 能识别仍被引用的旧段。读取路径取得文件句柄后，句柄生命周期覆盖定位读取。

checkpoint 在 writer 保护下同步文件并写出同一已提交边界，索引读锁可由 GET 共享。cleaner 的搬迁操作仍由 writer 串行化，逐条发布有效的新位置。旧段在新 checkpoint 成功持久化后才进入回收，快照 pin 继续约束删除时点。

追加或同步失败时，索引继续指向此前已提交内容。截断回滚失败会将引擎标记为需要重开，后续写入和 checkpoint 返回错误。现有记录格式、checksum 与原子批次恢复机制共同参与验证。

Rust 的 stats、checkpoint、rotation 和 cleaner 仍可能等待 writer。存储设备争用、索引短写锁、reader cache 与内存分配也可能影响读取，实验需要保留这些成本。

## 一致性如何验证

| 场景 | 验证内容 |
| --- | --- |
| 暂停提交 | 同分片其他 key 与异分片的热 GET 在解除屏障前返回，Rust 冷 GET 读取已提交值 |
| 周期 TTL | 写入暂停时扫描能够结束，后续热 GET 仍可完成，解除后清理继续 |
| 同键操作 | 后续 SET 与 GET 等待本 key 的在途提交，唤醒后重新检查状态 |
| 提交失败 | 缓存保留旧值，失败操作的版本与通知保持原状态，暂存预算释放 |
| 并发成功与失败 | 一个操作失败后，另一个已成功操作的值、版本和统计正确 |
| 多键与脚本 | MSET、EXEC、Lua 的执行隔离与 WATCH 冲突检测通过网络入口验证 |
| 生命周期 | Clear、Close 等待在途操作，停止与重启能够读取已确认数据 |
| 故障恢复 | 异常终止后恢复已确认的同步批次，部分尾记录按完整批次处理 |
| 维护与快照 | rotation、checkpoint、cleaner、snapshot 与 iterator 交错后视图正确 |

跨层提交的可见性存在顺序。Rust 索引先发布，返回 Go 后再发布缓存和版本，同 key 的提交登记覆盖这一段。Go 的正常命令通过统一协调入口访问数据。

单引擎 WriteBatch 是崩溃恢复的原子单位。EXEC 与 Lua 内部的多个数据库调用分别提交，异常终止可能保留已完成调用的前缀。跨库 MOVE 的崩溃中间状态也需要单独研究。

## 实验设计与论文表达

2026-11-17 核心对照采用当晚冻结的 Linux `start`、`candidate` 与 Redis。候选的性能改动位于 Go 的同 key 等待逻辑，Rust 源码与压测客户端沿用同一公共起点。交付还包含 CLI、空 bulk 的流式协议解析和演示程序修复，混合负载使用现有快速请求解析入口。上一轮 `baseline`、`go-only`、`final` 的源码在 Linux 重新构建，作为有限历史消融。两轮结果分别保留环境、方法和构建身份。

当前主矩阵使用 std 的 95/5 组与 gnet 的 80/20 组，Redis 在两组均使用自身 TCP 入口。数据为 32B value、10 万 key、64 连接，每个到达率三版本各六轮，正式测量 60 秒、预热 15 秒。到达率先校准后冻结，保留高负载复现中的过载与失败。完整安排见[本轮执行计划](thesis_12h_plan.md)。

固定到达率客户端从计划发送时刻计时到完整回复，保留发生器排队等待，同时输出目标率、实际发送率、完成率、超时与错误。读写分别报告 p50、p95、p99、p99.9。该方法参考 wrk2 关于协调遗漏的说明，协议客户端使用项目内的 RESP 实现。[wrk2 方法说明](https://github.com/giltene/wrk2)

同步确认方式在所有对照中保持一致。Redis 的持久化配置包含多种同步策略，外部参照需要记录实际配置与版本。本轮外部参照的可用性单独记入执行报告。[Redis 持久化文档](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

论文可将贡献表述为针对本项目的跨语言提交可见性设计、锁等待链分析、故障回归与可复现实验。锁拆分、私有暂存和提交后发布都有既有研究与工程背景，学术原创性需要结合后续文献检索和导师要求评估。

SILK 从 LSM 的内部 I/O 调度研究尾延迟，提供了分析维护操作和前台请求相互干扰的相关工作入口。Kerniva 当前采用 segment log 与内存位置索引，其实验结论需要针对自身实现建立。[SILK 原论文页面](https://www.usenix.org/conference/atc19/presentation/balmau)

## 三台虚拟机的后续验证计划

后续阶段可在三台 Linux 虚拟机部署单分片、一个 leader 和两个 follower。先固定成员，采用成熟 Raft 实现管理任期、日志顺序和多数派提交。副本应用已经提交的日志后发布缓存，将当前提交与可见性边界延伸到复制场景。

| 虚拟机 | 建议角色 | 初始资源 |
| --- | --- | --- |
| VM1 | leader，可轮换 | 2 vCPU、2GB RAM、独立数据目录 |
| VM2 | follower | 2 vCPU、2GB RAM、独立数据目录 |
| VM3 | follower | 2 vCPU、2GB RAM、独立数据目录 |

三台虚拟机共用一台物理机时，CPU、硬盘和故障域存在共享。配置需要记录宿主机资源，并分别测量宿主负载干扰。

分布式验证分为四步。

1. 固定 leader，建立复制、日志索引和多数派确认，验证重启追赶。
2. 加入 leader 故障、旧 leader 隔离和恢复，核查成功回复的数据与任期约束。
3. 注入 follower 慢盘、复制延时、丢包和网络分区，观察 GET/SET 尾延迟与可用性。
4. 区分线性一致读取与允许陈旧的本地读取，明确各自确认条件后进行对照。

验收包括多数派故障处理、旧 leader 写入隔离、日志冲突修复、快照安装、重放幂等和已确认写入核查。性能实验分别输出 leader 与 follower 的资源、复制积压、确认延迟和故障恢复时间。

这一阶段当前交付到方案，后续实施时再选择 Raft 库、RPC 与虚拟机网络配置。
