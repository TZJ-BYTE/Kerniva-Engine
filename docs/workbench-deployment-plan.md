# 桌面工作台的一键部署与实例管理计划

2026-11-25 草案，供下一轮决定范围。本轮交付设计计划。

## 用户第一次打开软件时能做什么

首页保留「连接已有数据库」，增加「部署 Kerniva」。前者填写本地或远程数据库地址，适合已有 Kerniva、Redis 或 Redis Cluster 的用户。后者首先提供「本机单机」预设，显示将安装的版本、运行位置、数据目录、端口和启动方式。接受推荐值即可点一次「安装并启动」。成功后直接出现「浏览数据」和「查看日志」。用户也可以先展开高级设置，选另一块磁盘或修改端口。

桌面本身继续提供便携包。另做标准安装器供需要选择软件安装位置、添加快捷方式和正常卸载的用户使用。关闭工作台后，长期部署的数据库由实例管理器维持运行；临时演示继续沿用原来的生命周期。当前打包的内容、数据库构建和复制原型分别已有独立入口。[桌面工作台](verification/native-workbench.md) · [数据库构建](../scripts/build.sh) · [复制原型](architecture/adr-0003-sealed-log-replication.md)

## 建议的交付顺序

| 阶段 | 用户得到的功能 | 验收方式 |
| --- | --- | --- |
| 1 · 本机单机闭环 | 安装工作台；一键部署单机；自选引擎和数据位置；启动、停止、重启；健康状态、日志和「打开数据目录」；分别设置桌面登录时打开、数据库开机运行 | 从没有 Go、Rust、Python 开发环境的系统开始，点一次部署，写入并读回测试键。关闭桌面后仍能连接。重启系统后，按所选策略核对服务状态、原配置和原值。关掉自启再重启复验。 |
| 2 · 数据与版本维护 | 多实例列表；配置差异预览；备份与还原到新实例；离线迁移数据目录；更换引擎版本；卸载程序时保留数据 | 同时运行两个实例，独立端口、目录、进程与日志。在迁移中断、目标盘不足、升级启动失败时分别复验恢复路径，核对键值、持久化位置和实例身份。 |
| 3 · 持久的一主两从 | 在 Linux 或选定 WSL 发行版上一键创建单主和两个只读副本，配置整理进程、端口与各节点的独立目录；从现有复制控制台查看进度、暂停和追齐 | 关掉桌面再打开，原拓扑仍在。断开一个副本并跨越主库日志回收点，恢复后由快照加后缀补齐；核对两从新写入、磁盘游标和断源重启。 |
| 4 · 远程主机运维 | 显式登记一台 Linux 主机，预览将部署的位置和服务，复用前述部署清单。之后再考虑多机拓扑编排 | 在独立远端主机首次安装、升级、断线重连和卸载；网络中断后能查询原任务结果，重复点击不会创建第二套同名服务。 |

首版以 Windows 工作台部署原生单机为目标。Go 日志已有 Windows 写锁与发布实现，仍需在干净系统上验证数据库服务、对应 Rust DLL 及系统重启后的数据读回。Linux 复用相同的实例清单和操作，再接入系统服务。当前副本程序使用 Linux 入口，Windows 桌面部署一主两从时应明确显示所选 WSL 发行版和 Linux 数据路径。macOS 先在真机完成桌面包验收，再验证后台服务与开机启动。已有远程数据库连接可继续使用；远端主机自动部署排在第四阶段。[Windows 日志实现](../internal/golog/platform_windows.go) · [Windows 服务端构建](../scripts/build.ps1) · [副本入口](../cmd/kerniva-replica/main_linux.go)

## 路径和自启动如何设计

| 用户设置 | 建议行为 |
| --- | --- |
| 工作台安装位置 | 放窗口和终端程序，允许用户选盘，便携版仍可直接解压。 |
| 引擎安装位置 | 按平台、CPU 架构和版本存放服务端、对应 Rust 动态库及所需组件。多个实例可共用同一版本。安装来源支持正式发布包和本地离线包，记录并验证版本和摘要。 |
| 实例数据位置 | 每个实例有自己的绝对路径。首次部署可以选盘。已有实例移动数据走「迁移数据」操作，展示源、目标、可用空间及预计停机；成功前保留旧目录。 |
| 配置和日志 | 每个实例分别保存配置和日志，界面展示实际生效的路径。修改设置前显示差异以及是否需要重启。记录数据库端口、所属主机、运行账户和服务标识，方便故障后重新发现。 |
| 自启动 | 「登录时打开工作台」和「系统启动时运行此数据库」分别设置。显示系统登记的实际状态及权限错误。无图形用户登录时开机运行，要单独用重启测试验证。 |

Windows 评估当前用户安装加专用服务入口，以服务控制管理器托管需要开机运行的实例；Linux 对应 systemd，区分用户会话和系统级服务；macOS 评估 Service Management 的登录项、agent 和 daemon。涉及系统服务注册时才请求对应平台权限。WSL 实例另行验证 Windows 启动发行版及 Linux 服务的完整链路，避免界面显示已开机启动、实际仍需先打开终端。[Windows 服务控制管理器](https://learn.microsoft.com/en-us/windows/win32/services/service-control-manager) · [systemd 服务](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) · [Apple Service Management](https://developer.apple.com/documentation/servicemanagement/smappservice)

## 数据和进程的管理边界

- 工作台保存的连接只授予相应数据库操作。对于外部已有的 Redis、手动启动的 Kerniva 或其他项目服务，继续提供连接与查看。「导入受管实例」需另行核对实际可执行文件、配置、数据路径、服务所有者。按实例标识和服务标识执行启停。
- 「安装并启动」分步落盘记录。检查端口、目录归属与磁盘空间，拒绝两个实例共用数据目录；解包并校验组件，生成绝对路径配置，再以服务账户核对文件存在、路径可访问及实际生效的设置。数据库目前在配置文件缺失时可回退默认值，部署入口应在启动前报告这个错误。启动后做 RESP 健康检查，最后登记成功。中途退出后可继续或回退，同一请求重复执行可取得原结果。[服务端入口](../cmd/server/main.go) · [配置加载](../config/loader.go)
- 数据迁移先正常停止写者与维护进程，再完整复制和验证，在新路径启动并读回见证值后切换配置。保留旧数据到用户确认释放空间。导入备份作为另一主库时，按既有来源 ID 规则处理复制分叉。[主库恢复边界](architecture/adr-0003-sealed-log-replication.md#从备份恢复主库)
- 「移除实例登记」「卸载引擎」「删除数据」分开操作。卸载软件时默认保留数据。仅在格式兼容时回退引擎版本，发生数据格式转换时通过经过验证的备份恢复。
- 桌面和鼠标终端应共享实例清单及部署操作。先复用引擎已有的 `host`、`port`、`data_dir`、`log_path` 等配置。现有根目录启停脚本按仓库的 PID、停止文件和日志路径管理单一实例，新管理器需要为每个受管实例独立保存这些状态。[配置样例](../config.golog.yaml) · [Windows 启停入口](../kerniva.ps1) · [Unix 启停入口](../kerniva)

第一次实施建议只验收阶段 1。用户能够自行选择磁盘、关掉桌面继续用数据库、重启后按预期恢复，才开始做已安装实例的数据迁移和拓扑管理。
