# 合并同步与一主两从验收

在 2026-11-24 的 WSL 2 ext4 上使用实际 TCP 进行验证。实验以单机小键值的固定负载和尾延迟为重点，并以同步持久化的 Redis 作对照。

文中 `logs/` 路径指实验机的本机归档，公开仓库提供复现入口与汇总数据。

## 单机正确性

Windows 和 WSL 的 Go 竞态检测与 Rust 测试通过。实际 net 和 gnet 请求验证了 WATCH 冲突、EXEC 运行错误、批量超预算、并发到期与续期、段封存失败、强制重启及合并后恢复。Linux 用子进程文件大小上限触发实际短写，校验回滚到原始字节并在重启后恢复已确认写入。

恢复原子单位是一个日志帧。MSET 失败全批回滚。EXEC 执行期间使用排他门，运行错误按命令返回，进程崩溃时可能保留已提交命令的前缀。同步成功到客户端收到回复之间的强制终止可能留下已落盘的完整写入。

## 固定速率对照

相同 gnet 服务二进制按开关对照逐次同步与最多 8 个请求的合并同步。预填 10 万个 32 字节值，64 个 TCP 客户端，均匀键分布。每组热身 2 秒，每轮测量 10 秒，三轮轮换运行顺序。Redis 启用 AOF 和 `appendfsync always`，旧后端启用同步。延迟从计划发送到收到完整回复，包含客户端排队。三项达标条件是零失败、实际和窗口内收发速率达到计划的 98%，以及队列无持续上涨。

| --- | --- | --- | ---: | ---: | ---: | ---: |
| 50% 写，3,000/s | Go 合并同步 | 3/3 | 2,998 | 0/90,000 | 1.221 / 1.446 | 9.667 / 12.976 |

| 50% 写，3,000/s | 旧 Rust 后端 | 0/3 | 774 | 42,850/90,000 | 1,999.666 / 1,999.666 | 1,992.294 / 2,000.412 |
| 50% 写，3,000/s | Redis | 3/3 | 2,998 | 0/90,000 | 22.544 / 40.501 | 23.921 / 43.123 |

表中给出各轮中位数，失败数累计。未达标窗口的成功请求延迟用于解释过载。50% 写时，三轮分别确认 14,914 次写入，合并后只执行 3,840、4,201、4,305 次提交同步，减少约 71% 至 74%。在 95% 读的两轮有效配对里，Go 逐次同步 GET p99.9 为 6.65 至 6.73 毫秒，合并后为 1.51 至 1.54 毫秒。

## Rust 后台快照与 Redis AOF 重写

WSL ext4，10 万小键值、64 个连接、50% 写、3,000 请求/s，各运行 20 秒 × 3 轮。四组均为 3/3 轮达标，且各有 180,000 个请求零失败。Go 日志使用 `GroupMax=8`，Redis 使用 `appendfsync always` 并关闭自动 AOF 重写，重写组在压测窗口内手动触发。

| 方案 | GET p99 / p99.9 ms | SET p99 / p99.9 ms | 主服务 CPU 单核% | 主服务峰值 RSS MiB |
| --- | ---: | ---: | ---: | ---: |
| Go 合并同步 | 1.315 / 19.399 | 22.151 / 43.909 | 25.3 | 68.9 |
| Go 合并同步 + Rust 快照 | 1.159 / 1.376 | 9.601 / 14.189 | 30.8 | 68.8 |
| Redis AOF | 7.717 / 10.584 | 7.733 / 10.813 | 7.1 | 29.5 |
| Redis AOF + 手动重写 | 16.908 / 33.423 | 16.908 / 35.652 | 6.5 | 29.8 |

Rust 每轮发布 18 次快照并回收约 11 MB 日志。它是独立进程，每轮采样约 0.90–0.95 CPU 秒和 20.1–20.7 MiB 峰值 RSS。Redis 重写每轮完成一次，报告的写时复制内存约 2.2–2.7 MiB。表中主服务数据来自三个独立窗口的中位数。两种维护的频率与文件格式不同，Go 不开整理时的尾延迟也有明显轮间波动。数据支持在本负载下能边写边完成 Rust 快照，以及开启整理时的实际资源开销。

原始记录在 `logs/golog-followup-bSuIKDwd/grouped-maintenance`。复测用 `--workloads uniform --read-percent 50 --rate sync=3000 --rounds 3 --duration 20 --maintenance-only --redis-rewrite`。

### 活动日志同步方式配对

在同一 WSL ext4 上对照仅将活动日志追加后的同步从 `File.Sync` 改为 Linux `fdatasync` 的实验二进制。文件创建、封存、回滚、目录同步和 Rust 维护均沿用原路径。两版使用相同 Rust 库和压测程序，均为 gnet、10 万个小键、64 个连接、50% 写入、8 帧上限，每轮预热 2 秒并测量 30 秒。交替运行次序。9,000 组第 4 对的候选窗口曾被任务切换中断，保留已完成记录，重新运行该窗口。

| 目标请求/s | 活动日志同步 | 容量检查通过轮数 | 全轮失败请求 | 窗口成功请求/s 中位数 | GET p99 / p99.9（ms） | SET p99 / p99.9（ms） |
| ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 3,000 | `fsync` | 3/3 | 0 / 270,000 | 3,000 | 813.695 / 1,086.325 | 843.055 / 1,111.491 |
| 3,000 | `fdatasync` | 3/3 | 0 / 270,000 | 3,000 | 1.147 / 1.331 | 3.236 / 16.908 |
| 9,000 | `fsync` | 1/6 | 300,691 / 1,620,000 | 6,527 | 1,969.226 / 1,999.660 | 1,973.420 / 2,000.683 |
| 9,000 | `fdatasync` | 2/6 | 268,159 / 1,620,000 | 6,592 | 1,971.323 / 1,999.753 | 1,973.420 / 2,000.637 |

表中延迟是各轮成功请求的分位数中位数，包含从计划发送时刻起的压测客户端排队。容量检查要求零失败，发送及成功速率均达到目标的 98%，且队列没有持续增长。3,000 组的 `fdatasync` 三轮 SET p99 分别为 3.24、1,048.58 和 3.21 ms，`fsync` 为 455.08、843.06 和 1,195.38 ms。第 3 轮 `fsync` 第 15 秒的 SET 客户端排队 p99 和完整回复 p99 分别约为 1,598 和 1,640 ms。每条测试连接一次最多有一个未完成的请求，同一连接上的 GET 也会随前方写入积压。该窗口没有逐次同步记录，无法区分始发延迟来自文件同步还是执行调度。

9,000 组最先完成的四个配对中，两版均掉量，平均每组约 7.9 至 8.0 帧，30 秒内完成约 12,600 至 13,000 个合并批次。第 6 对均零失败，两版各完成逾 37,000 个合并批次。实际排队随运行时段明显变化，已观察的名义吞吐和长尾需要分别评价。项目保留 `File.Sync`，并将 9,000 请求/s 记为过载探针结果。原始窗口、配对 CSV 和二进制校验位于 `logs/golog-followup-bSuIKDwd/fdatasync-paired`，候选构建脚本为 `logs/golog-fdatasync-probe.sh`。

### 同步等待与秒级排队复查

用上轮二进制跑 16 个 45 秒窗口，仍为 50% 写、3,000 请求/s。每种同步方式各有四个正常窗口和四个每约 50 毫秒采集一次线程、虚拟磁盘统计的窗口。同轮轮转观测顺序。全部通过速率检查，2,160,000 个请求零失败。无观测的 `fsync` 和 `fdatasync` 的 SET p99 中位数分别为 14.14 和 29.98 毫秒。此前的秒级排队未重现。

八个观测窗口中只有一个秒桶的排队 p99 超过 100 毫秒。该秒 SET 排队 p99 为 231.21 毫秒，前一秒为 1.12 毫秒。虚拟磁盘完成的 flush 约从 830/s 降到 554/s，每次已完成 flush 的累计时间均值约从 0.64 毫秒变为 0.86 毫秒。两秒均有 19/20 次扫描看到活动日志同步线程。共享设备计数包含其他操作，线程扫描对长等待更敏感。配对的无观测轮未出现该尖峰，现有数据只能说明同一秒有排队和磁盘活动变化。逐秒时间、读得到的线程、完整压测记录和分析脚本在 `logs/golog-followup-bSuIKDwd/proc-wait-probe`。

### 并发写入、自动整理与双进程故障

WSL 下的 `python3 -B scripts/golog-replica-check.py --stress` 同时运行两库写入、主库原子批次读取和从库稳定游标读取。它用本地中继把 B 的一次约 64 KiB 日志段截停在 1,024 字节，并检查其 `CURRENT` 仍指向已发布代。Rust 常驻进程在业务仍接收写入时回收该段。随后强制结束 B，以同一目录启动并核对全部种子键，再接通中继，用新快照和连续尾段补齐。

gnet 两次和 net 一次均通过。在三轮中，重启的 B 均从序号 10 恢复初始视图，随后使用截止到 1,142 至 1,322 的快照继续追赶。每轮有约 2,800 至 3,200 次并发写操作得到确认。终局先停止发新请求并收齐回复，确认两库的新写还位于活动日志后强制重启主服务。每个节点核对 1,164 个预期键位，含删除和到期键，并核对主库键数与绝对 TTL。原始时间线与摘要在 `logs/golog-followup-bSuIKDwd/stress-replica`。

### 旧备份启用新来源与游标发布故障

net 和 gnet 均通过旧备份场景。从包含旧来源 ID 的序号 1 备份恢复到独立主库目录。原副本已同步原主库上序号 2 的 `branch=old`，恢复目录则分别封存序号 2 的 `branch=new` 与序号 3 的新键 `tail=restored`。在源侧车运行时轮换会被共享锁阻止。对恢复目录轮换 ID 后，重开原副本能读到原序号 2 的旧值，报告来源变化，`CURRENT` 与尾键缺失状态保持原样。空目录上的副本从新来源同步至序号 3，同时读到恢复分支和尾键。常规同源重启与快照追赶也在两个入口复验通过。 [备份恢复操作](architecture/adr-0003-sealed-log-replication.md#从备份恢复主库)

WSL 焦点竞态测试分别在副本安装中临时游标同步后、重命名之前，以及 `CURRENT` 重命名后目录同步成功时发出 `SIGKILL`。关闭源端后用同目录重开，第一处恢复序号 2 的旧代，第二处恢复序号 5 的新代。三次重跑均核对了更新、删除、新键与废弃代清理。这里验证的是 Linux 进程强制结束。全量 Rust、Go 竞态与实进程结果在 `logs/golog-followup-bSuIKDwd/replica-recovery-boundaries-recheck`。

### 多库同时恢复的容量实验

在同一 WSL 2 ext4 实例上，把上一组冻结工件中的独立轮询副本用作 B。每档保留一个轻载库，其余库各安装 5,250,315 字节的快照和一个封存尾段。A 直连源。中继为 B 的每个慢库单独提供 512 KiB/s。观察到 B 的每个慢库都已有不完整的本地暂存文件后，向轻库依次写入三个独立标记。

| 逻辑库数 | 同时下载的慢库数 | 从 B 启动到两副本全部追齐，两轮 | B 峰值 RSS，两轮 | 轻库源端可取到 B 读到，各标记的延迟观测上界 |

| 2 | 1 | 10.09–10.11 s | 25.0–25.5 MiB | 52.9–131.9 ms |

八个正式窗口的 24 个标记都在全部慢库共同传输的时段内写入，并由源、A 的 GET、B 的 GET 和 B 的磁盘 `CURRENT` 分别观测到。各慢库逐一验证快照 SHA-256、尾段更新和删除，以及两个副本上各 160 个完整键值。16 库每轮向 B 实传 75.11 MiB 的快照及尾段。B 进程在收敛时的 Linux 存储写入计数为 75.32 MiB。

每个标记的延迟区间由同一单调时钟上的最后一次阴性采样和首次阳性采样算出。检查循环每轮休眠 25 ms，GET 和 `CURRENT` 的观察区间相交，不能用采样顺序区分二者的真实发布先后。原 2 库首轮收敛和校验通过，关闭测试中继时捕获一次 `BrokenPipe`。保留该记录，区分运行期与关闭期错误后在新目录复验，正式表使用两个干净窗口。
