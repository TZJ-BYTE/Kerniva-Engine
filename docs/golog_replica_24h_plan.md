## 如何认定原因和收益

1. **先校准测量。** 先用现有四个事件作粗计时，再在同一源码上比较粗探针与细探针；普通构建和诊断构建均由同一个外部观察者记录源可取、磁盘游标及首次正确 GET 的时间界。复用 ABBA、BAAB 顺序。预设可接受的细探针扰动为配对安装耗时中位变化绝对值 ≤5%。超过时先收窄探针再校准一次；仍超出则报告可支持的较粗时间范围。现有直连驱动要求前四条事件精确匹配，新增事件必须按请求/库关联，并从完整事件流选取对应边界；普通二进制使用外部观测入口。[直连驱动](../scripts/golog_replica_direct_delta.py) · [现有诊断构建器](../scripts/diagnostics/golog_idle_polling/build_phase.py)
2. **计时贴合真实代码。** 用单调时钟按次记录准备新代与链接旧文件、每段 `io.CopyN`、每段文件同步及关闭、响应末尾校验、Rust 增量校验/回放与 Go 读视图准备、两处目录同步、`CURRENT` 临时文件同步/重命名/最后的目录同步，以及读视图发布。以请求和文件为粒度，汇总每段字节数、次数、总耗时与最大值。复制调用同时包含源端读取和本地写入；Rust 回调也可能嵌套 Go 解码。保留嵌套关系和剩余时间，只有追加受控探针分开观测后才作更细归因。
3. **预先定义慢窗。** 在正式样本中，把“清单校验至 `CURRENT` 持久化 ≥2 s”标记为慢窗，也保留低于 2 s 的完整分布。一个阶段若在至少两个独立八窗块的慢窗中都解释了至少一半额外耗时，才可提议修改。额外耗时按该慢窗减同一实现、同一时段正常窗中位数计算；没有可比正常窗则留作描述性证据。同步记录 B 的进程 CPU/I/O、采样间隙及宿主可用磁盘；操作系统与进程的时间相关性只能作为线索。报告写明“慢窗数 / 有效窗数”，小样本列实值。
4. **按同一口径验收候选。** 同文件 A/B 采用八窗块，两种吞吐口径分别从请求到 `CURRENT` 持久化和读视图发布。沿用上轮退化筛查：四个相邻配对中，候选/基线吞吐比中位数 ≥0.95，且低于 0.90 的少于两对。首块越线或极差 >0.20 时，用原封存文件完整复验。要宣称改善长尾，还须在两个独立块中看到所定位阶段的慢耗时下降，并有普通构建端到端的同向证据；没有暴露足够的基线慢窗时，结论写“收益未证实”。任一键值、文件摘要、来源、游标、发布顺序或重启状态不符，立即隔离候选。同步持久化契约是验收前提。
5. **保留否决路径。** 可重复缺陷优先复现、修复及回归；若候选未通过、诊断扰动过大或主机耗尽资源，将最后已验收版保留在主线，交付完整原始证据和失败原因。若正确性问题也能在基线复现，独立记录其影响与最小复现。
