## 本轮完成的设计

毕设方向收敛为《面向小键值混合读写负载的内存数据库读延迟优化设计与实现》。研究的问题是同步落盘期间，无关数据的读取需要等待多久。

Go 为符合条件的普通 SET 保存私有待提交值，预留内存，等待 Rust 同步成功后发布缓存、WATCH 版本和通知。缓存命中且无 TTL 的 GET 可以与其他分片的提交并行。同分片仍按顺序访问。

Rust 将追加、同步与回滚放在 writer Mutex 下，将已提交位置放在独立 index RwLock 下。GET 在索引锁内取得位置和文件句柄，随后执行定位读取。原子批次整批发布，快照与旧段回收继续遵守引用和 checkpoint 持久化顺序。

周期过期扫描忙时延后，减少排队写锁对热读的连带影响。同时修复过期扫描 Start、Stop、Close 的并发生命周期。

设计、锁顺序和后续三台虚拟机计划见[毕设设计说明](thesis_read_isolation_design.md)。

## 测量方法

核心实验使用同步持久化、32B 字符串、10 万 key、64 条连接、noeviction 和 2GiB 近似缓存预算。主矩阵包括 std 与 gnet，以及 95/5、80/20、50/50 的 GET/SET 比例。原版和优化版使用相同到达率，交替版本顺序，每个配置测量三轮，每轮预热后测量 30 秒。

客户端按预定到达时刻生成请求，延迟从预定发送时刻计到完整回复，因此包含发生器和连接排队。每条连接同时只有一个请求等待回复。虚拟积压上限和从计划时刻起算的超时共同约束积压，所有计划请求都进入成功或失败分母。

GET 与 SET 分别报告成功请求的 p50、p95、p99、p99.9，超时、拒绝和网络错误单独计数。超时观测值受截止时间删失，不能用它推断请求最终实际完成耗时。报告中的 p99 汇总采用每轮 p99 的中位数，同时保留最小值和最大值。CDF 图合并对应轮次的成功样本直方图。

稳定性筛选要求零失败、实际发送与成功率及窗口内发送与成功率均达到目标的 98%，并且未触发持续排队增长规则。排队规则与每秒数据保存在 analysis/method.json 和 windows.csv。稳定性标记用于区分本机本轮的负载状态，容量上限需要更细粒度扫描和更多重复验证。

服务端 CPU 由进程累计时间差计算，以一个逻辑 CPU 的 100% 为单位。资源采样从启动标记前延续到客户端退出，包含请求排空、汇总和控制器轮询余量。RSS 是该区间每秒采样得到的峰值。Go GC 与堆信息通过前后 INFO 获取，也包含这一余量。过载时排空时长可能不同，因此 CPU 平均值只描述各例自身资源区间。客户端与数据库运行在同一主机，发生器和控制器的 CPU、调度及内存开销参与本轮环境。

部分运行的 NumGC 增加，而导出的 PauseTotalNs 增量为零。CSV 保留运行时报告值，零值无法证明没有停顿，进一步分析需要运行时 trace 或更细的观测。

压测中每个 key 的 payload 固定，SET 重写相同内容，以控制请求体和校验成本。数据更新可见性由独立回归测试验证。直方图采用分桶上界，量化相对误差不超过约 0.391%。

缓存受限实验使用 4MiB/10 万 key 与 1MiB/百万 key 的 Go 解码缓存预算。预加载后保留操作系统文件页缓存，结果描述 Go 缓存未命中的读取路径。介质冷读需要另行控制操作系统缓存并设计实验。

## 适用范围与待验证事项

- Go 并发热读要求缓存命中且无 TTL，普通 SET 的并发提交还要求已缓存的字符串、noeviction 和足够预算。同分片争用、冷读、类型转换、复杂命令和其他全局排他操作仍可能使后续热读等待。
- Rust 已通过冷读绕过同步等待的屏障测试。Go 服务的冷读入口仍使用全局协调，原生引擎的并行能力在服务层冷读上存在这一限制。
- 内存预算沿用近似 payload 口径。map、对象头、Rust 索引、版本记录与运行时分配需要结合 RSS 观察。持续繁忙可能推迟物理过期清理，访问路径仍检查逻辑到期。
- 单个 Rust WriteBatch 是恢复原子单位。EXEC 和 Lua 的多次数据库调用分别提交，异常终止可能保留已完成调用的前缀。跨库 MOVE 的中间状态另有双副本风险。
- 本轮使用本机 Windows。Linux、macOS 和真实断电故障仍需后续验证。Windows 的新 segment 目录同步入口目前直接返回，checkpoint 替换使用 MoveFileExW，其断电边界另需核验。本机未配置 WSL、Docker 或 Redis，外部 Redis 同等持久化对照留待 Linux 环境。
- 本轮记录端到端排队、进程资源和 INFO 统计。锁等待与单次文件同步耗时尚需独立观测，现有数据无法确定反向复测的根因。
- 三台虚拟机的复制、故障切换和网络分区已写入后续计划。当前交付围绕单机读延迟，分布式实现安排在后续迭代。
- 锁拆分、私有暂存和提交后发布具有既有工程与研究背景。毕设可陈述本项目的跨语言可见性设计、等待链分析、可靠性回归和可复现实验，学术新颖性由文献比较和导师要求进一步确定。

## 产物与复现

- 源码与入口保存在当前工作区，服务端、客户端和 Rust 动态库位于 `bin`。
- 基线、Go-only 和完整优化构建位于本轮结果目录的对应子目录。
- 自动压测入口为 `scripts/thesis-bench.ps1`，统计与绘图入口为 `scripts/thesis-analyze.py`。

- 汇总 CSV、统计规则和图片位于 analysis，完整命令与退出码位于 evidence。
- final/source-manifest.json 与 go-only/source-manifest.json 对应实际源码快照，Go-only 的 engine.rs、reliability.rs 使用基线版本。changes-from-baseline.json 单独记录本轮源码变化。

在已配置 Go、Rust 和 C 工具链的 PowerShell 中，从仓库根目录重新执行完整验收。

~~~

~~~powershell
& .\logs\thesis-20261115-001232\run-low.ps1 -SuitePrefix ('repeat-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
~~~
