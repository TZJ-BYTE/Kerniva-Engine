# Rust 内存内核无人值守开发计划

基线为 `3aa1784`，计划日期为 2026-11-24。目标是在现有 Go 服务保持可运行的前提下，把 Rust 主存后端从设计推进到可独立验证的原型，并为毕设留下可复跑的延迟与内存基线。后续按 [ADR 0001](architecture/adr-0001-wsl-rust-memory-core.md) 迁移 Go 字符串命令。

## 工作范围

- 先完成纯内存 `MemoryEngine`。提供二进制 GET、PUT、DELETE 和统计，键值全部驻留内存，使用可配置的分片哈希表。限制常驻键和值的字节数，超限写入保留旧值。RSS 另行测量，记录索引、分配器和旧读引用带来的额外内存。
- 核心验收通过后，加入绝对过期时间、NX/XX、按版本更新、跨分片原子 PUT/DELETE 批次。条件与写入在同一锁范围完成。批次按固定顺序取得受影响的分片锁，先校验预算和变更，再发布。用能一次观察多个键的读取验证原子可见性。
- 先建立 Rust 原生基线。Go 现有服务纯内存模式在 WSL 上作为之后的 TCP 对照。Rust 内存后端接入 Go 后再进行同层比较，分开报告 Rust 原生、Go 经 ABI、完整 RESP 三层。
- Go 接入排到下一轮。新接口规划单键优先写入调用者的可复用缓冲区，空间不足时报告所需长度，多键以一次批量调用为目标。阶段验收保留现有 ABI、事务、复杂类型及持久化数据兼容回归。

TTL 以同一次操作读取到的时间判断，当前时间达到截止点即视为过期。测试注入时间，覆盖截止点的前一刻、恰好到期和到期后覆盖。版本由实例分配，删除重建后也能拒绝旧版本。过期条目的逻辑可见性与实际回收分别验证。批次在修改前核对最终预算，覆盖重复键、跨分片读写及失败回滚。

## 实验方法与通过条件

1. 先预填充 100,000 个键、32B 值。筛选 1、4、16、64 并发和 1、16、64 分片，覆盖只读、95/5 和 80/20 混合读写。选 95/5 的 16 与 64 并发做至少五次同参数重复，轮换单分片与候选分片数的检测顺序。
2. 额外做单热点和至少一次 8 分钟稳定性检查。记录样本数、失败或拒绝原因、系统负载和 RSS。p99.9 尾部只有少量样本时，和样本数一起报告。原生闭环基准反映内核调用时间，端到端阶段再使用现有限速客户端测排队影响。
3. 当前阶段以可复跑、无数据错误和旧路径回归通过为验收。分片数的取舍由读写尾延迟、吞吐和内存的变化共同决定。纯内存与同步持久化分别立 baseline。与 Redis 的同负载对照留到 Go 接入，用与 Kerniva 等价的持久化配置、相同回环网络和独立数据目录。
4. Linux 文件检查在空工作目录用 `strace` 跟踪编译好的原生示例，区分进程启动读取和引擎数据文件访问。Windows 可先做功能与兼容回归，其时间数据单独标注为检查工具的结果。

### 原生基准入口

从仓库根目录执行。下面一组可用于预检参数和 JSON 字段。正式测量先编译 release 示例，再直接执行二进制，单独采样该进程的 RSS。

~~~bash
mkdir -p logs/rust-memory
cargo run --release --manifest-path kerniva_engine/Cargo.toml --example memory_benchmark -- \
  --shards 16 --threads 16 --keys 100000 --value-bytes 32 \
  --operations 4000000 --warmup-per-thread 10000 --read-percent 95 \
  --sample-every 4 --seed 42 > logs/rust-memory/native-s16-t16.json
~~~

热点使用 `--hot-percent 100 --hot-keys 1`。长测先用短测估计操作数，再调整总操作数和采样间隔以达到目标时长并控制压测工具自己的内存。保留 GET 和 PUT 各自的成功样本、失败次数和 p99.9 尾部样本量。JSON 含压测工具的采样和键目录内存，比较 RSS 时同时保留这些字段。

## 自动处理和交付

- 工作区另用开发分支，基线、运行日志与结果分开留档。每阶段记录开始时间、命令、退出码和结果路径。中断后检查产物对应的提交和参数，再继续未完成项。
- 临时端口冲突时换端口。疑似环境超时核实进程和日志后重试一次。能定位的代码失败先修复再重测。持续数据错误、竞态、超预算或批次部分生效时，停止后续性能实验，保存最小复现和日志。
- WSL 因启动设置不可用时，先完成能在 Windows 验证的代码、构建和测试。正式 Linux 测试保持待办。保留现有虚拟化开机设置及旧 WSL 数据。临时进程使用独立端口和目录，结束时只清理本次启动的进程。
- 交付源码差异和测试结果、原生基准命令与原始结果、未完成项及原因。下一轮从可选 Go 后端及三层测量开始。

## 连续执行的下一轮

原生短窗、文件 I/O 检查和原子语义均已通过，进入 RESP 联调和同步持久化验证。原始结果和对照条件记录在 [WSL 实验记录](rust_memory_wsl_report.md)。

1. 冻结初版内存 RESP 服务。用同一个 Go 二进制切换旧内存后端与 Rust 内存后端，另在同一 WSL 回环端口运行 Redis。三者关闭持久化。短窗校准通过后，冻结 15,000、45,000、90,000 请求每秒，用 64 个连接和 95% 读负载轮换测量。
2. 补齐关键字符串命令和其命令级测试。为 ABI 测实际 Go 包装器开销，将结果与 Rust 原生内核和 TCP 分开记录。阶段实验进程独占可用测量时段。
3. 实现单独的 Rust 同步 WAL 原型。先验收写入确认、进程终止、绝对 TTL 与版本恢复、尾部截断、完整记录损坏及同步失败，再评估整批日志写入与读等待。
4. 以持有分片锁同步的实现为基线，测同步 I/O 内等待和同分片读的尾延迟。继续通过对照分析判断是否值得在同步时让读请求访问旧的已提交值。保留相同日志语义和崩溃恢复测试。
